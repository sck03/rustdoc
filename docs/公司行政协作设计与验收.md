# 行政办公、人事管理与申请审批

> 2026-10-06：本文描述 Rust 应用的模块和操作边界。历史 C# 表结构、测试与独立产品包裁剪不作为当前验收证据。部署和数据库以[当前架构事实](./当前架构事实.md)为准。

## 2026-10-06 全流程复核与闭环规则

本轮按现有全部行政、人事、OA 及业务交接能力复核入口、权限、状态、通知、历史、重试和人员交接。用户确认多位办理人采用**任一位办理即可完成本次操作**：领导审批仍独立执行，记录实际操作人、时间、说明和版本。同一旧版本只能成功办理一次。会议开始与结束、借用品发放与归还是不同操作，可以由不同指定人员执行。

| 流程 | 闭环检查与本轮完善 | 明确边界 |
| --- | --- | --- |
| 组织、账号、权限 | 公司/部门 → 人员 → 本人账号 → 岗位权限；变更权限撤销旧会话，事务内复核 | 分工只额外开放已获批的指定记录，不改变原审批权限 |
| 入职、转正、调岗、离职、返聘 | 调岗/离职先核对未结申请、审批、会议、借用品与办理分工；离职停用账号 | 变动立即执行，生效日不得晚于公司业务日期；返聘不自动恢复登录 |
| 关联账号调整 | 更换账号先检查人员与原账号交接；候选账号变更部门同样检查未结业务和职责 | 不通过改绑绕过交接；历史申请人及附件归属不重写 |
| 请假 | 草稿/附件 → 提交 → 审批 → 销假归档；已完成时段继续防重 | 自然日/半天不冒充法定余额、排班或考勤结算 |
| 加班 | 明确时区与时长 → 审批 → 时段结束后确认；已完成时段继续防重 | 不自动计算工资或调休余额 |
| 出差 | 行程 → 审批 → 返程归档；已完成记录仍与同人请假/出差互斥 | 差旅报销另按凭证申请，不自动创建报销单 |
| 费用报销 | 精确金额/凭证 → 领导审批 → 财务接收及接收说明 | HandedOff 不代表付款；会计账、银行支付和付款打印各自独立 |
| 采购申请 | 需求/预算 → 审批 → 实际采购/验收说明 → 按实收数量另行入库 | 入库说明记录采购编号；尚无采购订单、分批到货或自动对账 |
| 通用申请 | 用印、证明、IT、维修等按事项分工 → 审批 → 指定人员办结 | 用印/证明提交必须选择具体事项；多人办理不改变审批链 |
| 会议室 | 每间会议室选择分工 → 占用检查 → 审批 → 场地/钥匙交接 → 结束/归还 | 分工支持 1–10 人；在途预约不允许停用或换分工编号，接任修改原分工人员 |
| 消耗品/借用品 | 物品组分工 → 申请 → 审批预留 → 发放；借用品继续分次归还 | 消耗品发放即结束；已归还退出待办理；未结借用不允许停用资源 |
| 公告、附件、通知、待办 | 发布/确认独立，附件沿用记录授权；六类获批申请在实际完成前保留申请人待办 | 提交/修改重审提醒审批人；获批提醒办理人；交接与办结使用不同通知，已读不完成业务 |
| ERP/外贸衔接 | 客户、供应商、商机、单证和付款打印沿用各自权限、状态；OA 以编号、凭证及说明交接 | 未实现的采购自动入库、费用核销、总账、薪酬和 WMS 不以同名页面或一次批准代替 |

会议室与物品继续使用原单步资源审批，六类 OA 保留单步/指定步骤/部门链与直接代理。普通办理人仅额外读取获批及已交接/完成的分配记录；分工变更后，旧人员不能借旧通知绕过当前权限。原公司范围查看权限仍有效。

共用 `engine::handling` 管理分工、授权、快照与资源状态；`office_workflows` 管理交接/库存事务，`oa` 管理六类审批，`communication` 管理通知，`worklist` 管理待办，`personnel` 管理人员关联。原 `oa/handling.rs` 的二分类实现及资源处理重复分支已合并，沿用 records 和 schema 7。React 复用分工选择器，页面、hook 和 model 分责；保存或部分失败后同步刷新行政查询与待办。

## 2026-10-05 行政、人事、OA 与业务协作闭环

本轮按完整工作链检查组织、账号、人事、六类申请、会议资源、物品库存、公告通知、待办和交接，采用“申请人—审批人—办理人”三种职责。总经理、部门负责人等领导负责决策，管章、人事证明、物品保管等岗位负责获批后的实际执行；不能以审批通过代替盖章、交付、收货或付款。

```mermaid
flowchart LR
  A[公司部门与员工档案] --> B[关联账号与岗位权限]
  B --> C[申请与附件]
  C --> D[按审批步骤审核]
  D -->|驳回或撤回| C
  D -->|全部通过| E[对应岗位待办理]
  E --> F[实物交接或验收记录]
  F --> G[办结归档与历史查询]
  B --> H[调岗离职核对]
  H --> I[未结申请、借用品、审批及保管职责交接]
  I --> J[任职变更与账号处理]
```

| 环节 | 业务事实与责任 | 闭环入口及边界 |
| --- | --- | --- |
| 入职、转正、合同 | 人事维护档案、公司部门、工号及任职记录；管理员关联账号和权限 | 通讯录只公开工作联系信息，证件与档案附件单独授权；试用及合同到期进入待办 |
| 请假、加班、出差 | 本人提出申请，负责人审批，时段结束后销假、确认实际加班或返程归档 | 审批中心新增待办理视图；我的待办统一显示审批及归档工作。自然日/半天只是时长，不冒充法定假期或年假余额 |
| 用印、证明、IT、维修 | 具体事项与保管/办理人员分开配置；领导全部批准后交专岗执行 | 具体印章、证明事项、附件、审批历史、当前办理人员、办结说明相互关联。用印及证明提交前必须选分工 |
| 采购、行政物品 | 采购申请记录需求及预算，审批后登记采购验收；保管人按物品组入库、发放、接收归还 | 采购验收与库存入库各有真实操作，入库说明可登记采购申请编号；不自动用预算增库存，也不把采购申请当采购订单 |
| 报销与财务 | 申请人提交凭证，领导审批，财务接收资料并填写交接编号 | HandedOff 仍仅代表财务交接；会计记账、付款和对账由独立财务软件办理。付款打印单保持独立 |
| 会议室与借用 | 申请/登记、资源占用、使用/发放、钥匙/物品归还 | 取消释放预留；借用品支持分次归还。物品待我办理排除已发放的消耗品，避免完成后长期挂账 |
| 公告与通知 | 发布和确认阅读独立；通知只提醒业务变化 | 获批、办理、分工交接与通知同事务；通知已读不代表审批或实物交接完成。原审批前的隐私边界继续有效 |
| 调岗与离职 | 核对本人未结申请、在途审批、会议/借用品及保管职责 | 保管事项单列名称及数量并提供设置入口；先指定接任人员，再办任职变更。账号禁用仍可用于紧急撤权，失效权限不会继续放行业务 |

### 按事项和物品组配置办理分工

管理员进入“申请与审批 → 审批规则与代理 → 办理分工”，分别维护公章、合同章、在职证明等事项，以及日常用品（卫生卷纸、抽纸、垃圾袋）、服装辅料（服装吊牌、色卡、布料卡）等物品组。这里的名称均由公司自定，代码不按行业或某个物品名称设置特殊分支。每项最多 10 位办理人员，任一有权限的指定人员办理；审批仍按原审批规则逐步执行，办理分工不改变审批链。

普通办理人员只需相应模块的查看和完成登记/物品发放权限；即使数据范围为本人，也可在审批通过后读取并办理分配给自己的记录及其附件。入库、盘点、归还等动作另行授权。非指定人员即使拥有普通公司范围的完成/发放权限，也不能代办已明确分工的事项；管理员保留本公司的接管能力。原来具有公司范围查看权限的领导仍可按原授权查看申请，不通过分工收回其明确授权。

消耗领用与借用是每件物品的独立属性，不由物品组或名称推断。卷纸、抽纸、垃圾袋、一次性吊牌等一般设为消耗领用，发放即完成，不填归还日期，不出现归还按钮，不计待归还及离职未清数量；原记录仍留作领用历史。只有明确勾选“借用后需要归还”的实物才跟踪截止日期和分次归还，例如需要回收的样品色卡。产生领用记录后不能更换归还属性，以免篡改已交接事实。

通用申请保存所选分工编号与事项名称，会议预约保存会议室分工快照，物品申请保存物品组快照。修改分工人员后，未结业务立即由新人员承接，生成交接事件及接任通知；旧人员不能借旧通知继续读取超出当前权限的内容。既有名称、单位、归还类型、审批步骤和实际办理事件不会被配置变化重写。已引用的分工不能删除或改变类别，可停用新选用并继续处理存量。物品未结申请存在时不能更换物品组，人员交接应直接改该组负责人。

没有分工的历史记录保留原权限规则，不猜测历史管章人员，也不批量改写业务库；新用印、证明提交必须明确事项。物品可逐步补充分组，未分类物品仍按既有权限维护。部门/公司权限、当前账号启用状态、版本冲突、审批前附件冻结、重复请求和库存事务约束同时生效。

## 导航与职责

行政人事与六类 OA 的正式团队场景属于 Full 多用户版。2026-09-30 按用户要求，本地另提供 Full + SQLite 单机测试便携包，便于完整界面和登记流程测试。SQLite 保留操作员选择人员、登记批准结果的语义；它不替代 PostgreSQL 的本人发起、禁止自批、权限和并发验收。Document/Sales 不开放行政人事，Administration 不单独打包。

| 导航 | 页面 |
| --- | --- |
| 工作台 | 我的待办、公司公告、站内通知、申请与审批、工作概览、付款报销打印、文件任务 |
| 人事管理 | 人员档案、公司通讯录、员工请假、加班申请 |
| 行政办公 | 会议室预约、物品领用、费用报销、出差申请、采购申请、通用申请 |

请假属于人事与 OA 审批的交叉范围。报销的提交和审批属于内部协作，记账、付款和总账通常属于 ERP 财务。本项目已有独立财务软件，因此新功能只管理申请、附件、审批和移交：报销最终状态为“已移交财务”，不产生原付款记录、不套用付款报销模板，也不执行付款或会计记账。

2026-09-30 用户确认财务范围为“查看并接收已批准的报销单及凭证”。费用报销页提供“报销申请 / 财务接收”视图；内置 Finance 角色默认进入待接收列表，可以按授权的公司/部门范围读取已批准和已移交记录、下载凭证、查看审批历史并登记接收说明。内置 OfficeManager 默认负责审批，不再默认获得报销接收权限；Admin 可完成两步。自定义权限仍由“财务查看与接收”（complete）及数据范围控制，不按角色名称在业务代码中特判。财务普通查询保留本人范围，财务视图只能查询 Approved/HandedOff，详情/历史/附件复核当前状态与范围；不能借财务入口读取他人的草稿或待审批单。

接收复用版本控制的完成操作和已有 HandedOff 状态，保留办理人、时间及接收说明；历史“已移交财务”记录不伪装成已付款，不增加支付、银行或会计分录。设计参考 [Odoo 19 报销处理](https://www.odoo.com/documentation/19.0/applications/finance/expenses/approve_expenses.html)与[员工报销付款](https://www.odoo.com/documentation/19.0/applications/finance/expenses/reimburse.html)的职责和状态分离；本次实际阅读其官方 documentation 仓库对应源文档，仅采用授权队列、审批凭证与财务接收的衔接。

采购功能管理需求、数量、预算和验收记录，不建立采购订单、应付账款或第二套仓储系统。物品领用继续使用既有库存、预留、发放和归还流程。此次不包含薪资、考勤打卡、排班、法定假期计算和假期余额扣减。

## 会议室与物品的流程边界

“申请与审批”同时提供六类 OA 和会议室、物品入口，只有资源查看权限的账号也可进入。共用人员搜索、版本冲突保护、权限和办理历史，各自保留必要的业务规则：

| 项目 | 会议室／物品 | 六类 OA |
| --- | --- | --- |
| 提交 | 团队直接待审批；Full SQLite 登记后待交接／发放 | 保存草稿、核对附件、再提交 |
| 审批 | 团队按资源审批权限单步办理，禁止自批 | 默认单步，可配置逐级审批和代理 |
| 修改 | 交接前可修改；团队重新审批并释放旧库存预留 | 待审批先撤回；批准后不能直接修改 |
| 完成 | 会议结束／钥匙归还；消耗品发放即结束；借用品分次归还 | 按各类型登记办结／财务接收 |
| 提醒 | 资源记录、“我的待办”及审批中心；会议室和物品均有提交/重审、获批、交接/归还及分工变更通知 | 审批中心、持久通知、手动催办 |

Full SQLite 资源记录页默认显示全部状态，避免隐藏直接进入 Approved 的登记；中心显示待使用／交接和待发放。团队中心资源计数是当前权限下可见的待审批申请，不声称全部都能由本人审批；办理时仍复核审批权限和禁止自批。资源记录保存时的名称、单位、钥匙和归还类型用于历史显示与待办，资源改名不覆盖历史；物品已有领用记录后禁止改变单位或归还类型。无库存变化的申请提交、驳回和取消不递增物品库存版本。

## 六类申请

| 类型 | 专用内容 | 批准后的处理 |
| --- | --- | --- |
| 请假 | 假别、开始/结束日期、上午/下午、事由 | 时段结束后销假归档；时长按自然日、半天计算 |
| 加班 | 包含时区的开始/结束时间、地点、事由 | 时段结束后确认完成；每次 15 分钟至 24 小时 |
| 费用报销 | 币种、费用类别、发生日期、逐项说明和金额、凭证 | 记录移交对象或独立财务软件接收编号 |
| 出差 | 目的地、出发/返程日期、事由 | 返程后登记完成 |
| 采购 | 品名、规格、数量、单位、预算单价 | 记录采购和验收结果；不自动影响物品库存 |
| 通用 | 用印、证明开具、IT 支持、维修、其他事项 | 记录交付内容并办结 |

金额以十进制字符串传输，用 Rust Decimal 计算，不用浮点数。费用明细与采购明细各最多 100 行；采购逐项乘算并四舍五入到分后合计。日期使用严格自然日类型，加班使用 RFC 3339 时间点，界面按公司的业务时区转换。

六类申请均可在填写时选择受支持的图片、PDF、Word 或 Excel 文档，点一次“保存草稿”完成资料与附件保存，核对后再提交审批。后台先保存草稿，再按版本顺序上传；文件部分失败时保留已保存草稿和未确认文件，重试只继续剩余文件，相同名称/内容的上传重试不会重复存储。取消窗口只放弃尚未保存的部分，已保存草稿仍可回访。待审批期间内容和附件冻结；需要补充时撤回为草稿。驳回后可编辑并重新提交。批准后只能登记完成或由有审批权的人员作废，不能直接修改已批准内容。取消、撤回、驳回、作废、完成和移交须写明原因或办理结果。团队模式禁止本人审批本人申请。

人员、状态、版本和重叠校验都在同一事务中复核。请假与出差互相检查待审批、已批准及已完成时段，加班检查同类重叠，办结不会解除同人时段冲突。相同请求编号和相同内容返回原申请，编号被用于不同内容时拒绝；并发审批只有一次成功，过期界面返回 409 并保留草稿。

## 附件和历史

六类申请、人员档案和公告的文档支持 PDF、PNG、JPEG，以及 Word（DOC/DOCX）、Excel（XLS/XLSX）；每个文件最多 10 MiB，每份记录最多 20 个、总计 50 MiB。费用报销提交前至少上传一个凭证。服务端校验文件名、实际类型、扩展名和容量；Office 容器复用已锁定 ZIP/CFB 库，限制 ZIP 条目及展开总量，验证主文档与类型标记，拒绝损坏/伪装文件，DOCX/XLSX 不接受宏项目。文档只原样保存、下载，不执行宏、不做 Office 在线编辑或导入业务数据。图片执行有界解码，附件按摘要检查重复和下载完整性。

员工入职/编辑表单同时提供头像、身份证正反面及档案文档选择；头像/证件图片每张 5 MiB，档案文档采用上述类型和数量/容量限制。档案详情“照片与证件”显示已保存文档并提供下载和有原因的移除。文档使用人员记录版本和详情权限，离职后冻结；通讯录只开放头像及工作联系方式。工号继续全系统唯一，不改为按公司重复编号。

附件元数据和二进制分别进入当前数据库的 `records` / `files`，随现有备份恢复；不写用户临时路径、不新增上传目录或匿名公开地址。下载和删除先校验所属申请、公司和当前权限；知道附件编号不构成访问权限。下载保留原文件，PDF 以附件方式返回。

办理事件使用独立 `oa-event` 记录，保留操作人快照、时间、原因和申请版本，按页读取。修改申请不会覆盖先前的审批记录。申请不提供硬删除入口，人员、账号、公司与部门的历史引用会阻止误删。

## 账号、权限与人员交接

### 岗位、共享分组与账号单独配置

Full 新建账号默认“普通员工”（OfficeEmployee）。默认开放公司通讯录、本人会议室/物品与六类申请、公告通知，以及本人付款报销、个人票据模板设计和打印；不开放私密人员档案、审批、人事管理操作、发票报关或销售。普通员工登录进入申请与审批；付款报销打印、公告通知和文件任务在工作台，模板管理在资料与工具，各岗位分组位置一致，未授权分组隐藏。管理员及兼有单证/销售职责的账号保留对应业务导航。

“权限方案”就是共享的岗位权限分组，一个账号选择一个分组；可复制现有方案后修改，也可从空方案开始。权限来源按以下顺序确定，不叠加多份方案：

团队入职建议先维护公司、部门和员工档案，再创建普通员工账号并在人员档案关联该账号，最后按职责分配共享分组。PostgreSQL 的本人申请依赖有效的人员账号关联；通讯录访问不自动授予私密档案权限。

1. 账号单独配置：`permissionGrants` 为数组，完全替代岗位/分组；空数组明确不开通任何业务。
2. 指定共享分组：随该分组的保存内容更新；分组停用或不存在时拒绝业务访问。
3. 岗位默认：读取同名内置分组。未经管理员保存的系统种子（版本 1）采用当前正式契约的岗位默认；保存后版本递增，固定采用管理员选择。自定义、已编辑分组及账号独立权限不会被新版默认覆盖；关闭模块继续生效。读取不改写数据库、版本号或历史。

账号编辑器可将当前分组的可授权操作复制为独立配置，之后不会继续跟随该分组；恢复继承时丢弃独立配置并重新使用所选分组。旧账号保留原岗位和数据，不批量改为普通员工。系统管理员由身份固定授予本产品全部能力，不能用普通分组伪装成受限管理员；最后一个启用管理员仍不可删除或停用。

切换独立/继承来源保留账号额外关闭模块，复制时还带入分组的关闭模块；继承状态明确列出额外限制，避免切换来源意外重新开放。停用的共享分组显示空有效权限，原操作配置保留。查看和办理动作各自授权；自定义 OA/财务账号须保留必要的查看入口，接收权限不自动扩大普通查询范围。完整模块核对见[导航与权限闭环](./导航与页面简化说明.md)。

每个资源的查看、编辑、审批、导出等操作使用目录中已有的动作及本人/部门/公司/全部数据范围。关闭模块同时隐藏入口并从服务端最终权限中移除，技术依赖也不能重新打开被关闭模块；原操作勾选保留，重新开放后恢复。关闭入口不会删除业务记录。人员档案和通讯录共享页面模块开关，但私密档案仍由独立的“查看详情”等操作控制。

账号或所继承分组更新会使相关旧会话失效，重新登录后取得当前权限；独立账号不因无关分组修改而撤销会话。写入仍在业务事务内复核当前授权，版本冲突保留草稿。共享分组显示继承账号数量，账号列表支持按姓名、岗位、分组和部门查找。配置字段复用现有 records 存储和备份，数据库 schema 仍为 7。

### 审批方式、代理和催办

管理员从“申请与审批 → 审批规则与代理”按本公司六类申请分别配置：

| 方式 | 规则 |
| --- | --- |
| 单步审批（默认） | 有对应审批权限及数据范围的人员办理；PostgreSQL 禁止本人审批，SQLite 保留登记批准结果 |
| 指定审批人 | 按 1–10 个明确账号顺序审批；一个账号也可构成单步流程，不允许重复或申请人自批 |
| 部门负责人逐级 | 从申请人部门到顶层部门，读取负责人关联的在职账号；跳过申请人本人及重复负责人，缺失负责人/账号、越界或循环时阻止提交 |

提交时保存规则版本、步骤和审批人姓名快照。在途申请不会因修改规则、调换部门负责人而被重新指派；需变更时由申请人撤回，再按最新规则提交。驳回后重提也重新生成步骤，历史事件保留旧步骤和办理记录。每一步批准后仍是 Pending，所有步骤通过才是 Approved，财务此时才可接收。指定审批人及代理均须拥有当前查看/审批权限与相应数据范围；组织链不自动扩大岗位权限。

管理员配置直接代理的起止时间与启用状态；开始时刻包含、结束时刻不包含，同一原审批人的有效代理不能重叠。不递归代理，申请人不能代理自己的审批，同一人不能代批同一申请的多个步骤。每次办理重新核验原审批人和代理权限，记录原审批人、实际办理人、时间、说明和代理编号。默认权限池单步没有指定原审批人，需要明确代理时可用“指定审批人”配置单人步骤。

代理待办计数和分页同时使用原审批人的当前启用状态、公司以及查看/审批数据范围。原审批人停用、撤权或范围收紧后，无权办理的申请不再进入代理待办；详情和实际审批使用相同约束。恢复有效权限后可继续办理，既有步骤快照不改写。

审批设置的草稿独立于查询刷新。其他管理员并发保存引发版本冲突时，保留本人的未保存规则、代理和错误提示，不能自动替换或使用新版本覆盖他人设置；“重新载入审批设置”须先确认放弃本地修改，取消确认继续保留草稿。

申请人可对 Pending 申请手动催办，每份申请每小时最多一次，催办和通知同事务保存，只通知当前可办理步骤的人员。催办不批准或推进申请；这里不提供后台定时催办。审批中心和“待我审批”在数据库计数分页前筛选当前步骤及有效代理，财务待接收另列；审批后的通知使用当前权限和状态验证。

Full SQLite 测试包允许管理员关联人员账号，便于验证组织审批链；正式 Document/Sales 仍无此入口。指定步骤中的未结审批纳入人员/账号交接检查，已办理步骤和代理历史阻止误删账号。仍待完成的旧申请继续按其原有单步语义办理，不把新规则强加到历史在途记录。

- 每类申请有独立资源权限：查看、新建、编辑与提交、取消、审批与作废、完成登记；报销的完成动作显示为“移交财务”。账号和权限方案界面使用同一生成目录，不维护第二套权限表。
- 公司员工及原有业务岗位默认获得本人申请能力。行政管理员审批本公司行政申请，人事管理员审批本公司请假/加班。行政管理员不会因此获得私密人事档案权限。
- 本人、部门、公司范围在数据库查询前应用；列表、详情、事件和附件一致。管理员和“全部”范围也不能越过新 OA 的公司边界。修改前在事务内重新读取当前账号和权限方案，停用/变更权限不能用旧界面继续写入。
- PostgreSQL 团队申请必须由已关联在职员工的账号本人发起，不能通过传入人员编号代申请。保留的 SQLite 测试宿主允许操作员选择人员登记，并标记“登记批准结果”；正式两版单机的权限目录不开放 OA。
- 草稿、待审批、驳回待处理、已批准待完成的申请纳入离职和调岗交接。必须先取消、办结或移交，再执行任职变更。已完成历史保留原公司、部门、人员和申请人，不随调岗批量改写。
- 人员改名、调岗及离职与关联账号在同一事务更新；离职立即停用账号并撤销旧会话，返聘后仍由管理员明确启用。入职请求和附件支持安全重试，编辑档案保留已有头像、图片及文档。不能通过额外请求字段绕过管理员账号关联入口。

原有人员档案、账号关联、公司通讯录、会议室和物品流程继续使用既有服务。通讯录不返回身份证和私密人事字段；会议室继续检查预约冲突和钥匙交接；物品继续原子预留、发放与分次归还。

## 分层与存储

`export-doc-domain::oa` 管理日期、金额、时段和状态规则；`engine::oa` 管理申请、授权、事务、附件和事件；`export-doc-storage::RecordQuery` 提供公司/部门/所有者/人员/父记录/状态过滤和数据库分页。React 的 `features/oa` 负责此能力，复用 `features/office` 的员工选择器和基础对话框；模型、客户端适配、查询 hook、表单、详情及路由分开。

保留版本 5 建库基线，schema 版本以当前架构事实为准，按有序事务迁移保留数据。共用当前数据库的 `records`、`files` 和审计表，申请记录分为 `oa-leave`、`oa-overtime`、`oa-expense`、`oa-travel`、`oa-purchase`、`oa-general`，OA 附件/事件有独立记录类型；人员文档元数据属于人员记录，二进制按人员外键保存，无新表或 schema 变更。SQLite 与 PostgreSQL 共用公司分页、人员状态及父记录索引。旧试验库处理和升级边界以当前架构事实为准。

正式团队拓扑仍为单 API 实例加 PostgreSQL 18、多浏览器用户，PostgreSQL 使用有界连接池。六类 OA 的列表和历史已下推分页；会议室和物品的专用列表仍在应用层过滤分页，不能据此宣称无限数据规模或多 API 高可用。

## 参考与验证

### 公告与站内通知（2026-09-30）

发布管理员进入公告页默认显示含草稿的管理列表，列表直接提供“继续编辑”和“查看与管理”；编辑前读取最新详情与附件，保存仍校验版本。从未发布的草稿（含误归档的未发布草稿）可在详情中填写原因后删除，正文及附件在同一事务移除，删除审计保留；已有发布版本或阅读回执的公告只能归档。归档不是删除，发布过的内容继续供历史追溯。

两项能力面向 Full：正式团队运行于 Web/Docker + PostgreSQL 18，本地 Full + SQLite 测试便携包也可使用，便于免部署检查完整界面及流程。Document/Sales 单机没有入口，管理员直接请求也返回 403。公告与通知均持久保存到现有业务库，页面操作提示不代替通知。

| 能力 | 当前范围 | 作用 |
| --- | --- | --- |
| 公司公告 | 标题、纯文字正文、受控文档附件（类型见“附件和历史”）；草稿、发布、撤回、归档；本公司全体或一个指定部门；置顶和有效期；未确认筛选及主动确认阅读 | 发布放假安排、制度变更、内部通知 |
| 站内通知 | 提交、步骤通过和催办通知当前审批人及有效代理；最终通过/驳回、批准作废、办结/移交通知申请人；最终通过另通知相应财务/办理人员；物品获批、实物交接及办理职责变更同样通知对应人员；个人收件箱、未读数、单条/全部已读和关联业务入口 | 提醒办理或查看结果，复用现有申请与待办 |

公告查看、发布管理、回执统计是独立权限。内置岗位默认可阅读公告及自己的通知，行政管理员另有本公司发布和回执权限；自定义权限方案由管理员显式授权。普通读者只获得本人当前发布版本的确认时间；有回执权限者可分页查看各发布版本的确认人及时间。公告和通知均不越过公司边界；列表、详情、附件和关联业务复查当前权限，调岗、离职或撤权后不能借旧通知访问资料。

公告先保存草稿，再明确发布；发布后的正文、受众、有效期、置顶和附件冻结，须撤回再修改，归档后不可修改。有效期以含时区时间点保存，开始时刻包含、结束时刻不包含；未生效、过期、撤回和归档公告不会出现在普通读者列表。发布管理员可在管理列表查看本公司全部状态。重新发布递增发布版本并保存内容快照，旧回执保留但不会确认新版本；打开详情不会自动确认，必须点击“我已阅读并确认”。重复确认不会产生重复回执。

通知和 `oa-event`、申请状态在同一事务内保存，以事件编号和接收人组成唯一标识；事务失败全部回滚，重复审批冲突不产生额外通知。标记已读不完成审批或待办。接收人须为启用账号且有当前关联业务查看权限，通知分页/未读数在存储层按这些权限过滤；关联申请仍使用原 API 授权。页面在前台每 30 秒刷新，可手动刷新，不提供即时推送。

`engine::communication` 编排公告和通知，`domain::announcement` 管理有效期和状态规则，`storage::CommunicationQuery` 在 SQLite/PostgreSQL 中统一筛选后计数分页。公告和 OA 共用 `engine::record_documents` 的附件校验、容量、摘要、冻结、下载与版本控制，旧 OA 独立附件文件已合并。新记录类型为 `announcement`、`announcement-publication`、`announcement-receipt`、`announcement-attachment` 和 `site-notification`，沿用 records/files、审计及备份，不增表、不改 schema、不添加依赖或第二数据库。组织/账号的公告通知历史引用阻止硬删除。

### 现有申请流程

流程参考 Odoo 19 官方文档的[请假](https://www.odoo.com/documentation/19.0/applications/hr/time_off.html)、[费用审批](https://www.odoo.com/documentation/19.0/applications/finance/expenses/approve_expenses.html)与[采购需求](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/purchase/manage_deals/rfq.html)。实际阅读对应官方 documentation 仓库源文档；只借鉴申请、审核、凭证和办结职责，不依赖其产品，也不复制完整 ERP 财务功能。

- `oa_service` 和 `support/oa_contract.rs`：六类申请、精确金额、幂等、重提、撤回、附件冻结、下载回读、并发审批和交接；团队测试复用同一场景。
- `test-native-postgres.ps1`：隔离 PostgreSQL 18、独立业务账号、存储合同、OA 团队流程及灾备；ignored 不计为已通过。
- `communication_service`、`support/communication_contract.rs` 与存储 `support/communication_query.rs`：单机版本拒绝、公告生命周期、时区、范围过滤、回执版本/幂等、附件、事务回滚、通知去重和撤权；团队实库复用同一合同。`npm --prefix apps/export-doc-web run test:communication-ui` 使用隔离 React/Rust HTTP 宿主验证发布、附件下载、回执、重新发布、通知已读/业务跳转、窄屏和无障碍。实际执行结果见本批进度。
- `cargo build --locked -p export-doc-server --example office_review` 后运行 `npm --prefix apps/export-doc-web run test:oa-ui`：真实 React、生成客户端、Rust HTTP、SQLite 的六类操作，包含中文字段、PDF 上传、办理历史、桌面/手机布局；示例仅监听回环地址并使用显式隔离 DataRoot。
- 导航模型、无障碍、样式、缩放和视觉基线继续走现有检查。Tauri 窗口、其它 OS/架构和真实业务验收分别记录。

本批最终结果记录于[进度](./程序改进重构进度文档.md)。系统级 Authenticode、Developer ID 和 Apple 公证保持关闭；Tauri updater 的签名与公钥信任合同保留。
