# 人员、账号、组织与行政审批

> 2026-10-24：本文描述当前实现和使用规则。部署与数据库以[当前架构事实](./当前架构事实.md)为准；本批执行证据见[程序改进重构进度](./程序改进重构进度文档.md)。

## 默认规则

“删除误录档案”是纠错操作，管理员有权限，但档案存在引用时会禁用。详情现在显示具体原因：关联账号、正式任职/关联历史、行政申请、会议室/领用记录，或仍担任部门负责人。只有负责人引用时可先在组织架构清除或更换，再重试；已有业务历史的人员通过任职/离职流程处理。新建后的资料编辑、照片和附件维护本身不会阻止误录纠错。前后端使用相同限制，管理员也不能绕过引用检查强删历史。

采用用户确认的“**人事直接办理，按需启用审批**”。人事日常维护档案、办理任职变动；管理员可按公司制度分别开启入职、转正、调岗、离职、重新入职审批，默认全部关闭。管理员保留直接办理、档案纠错和账号管理权限；任职变动与登记纠错需要填写原因并留痕。

小团队可直接办理，需要负责人确认的事项再单独开启，例如只对调岗和离职启用审批。联系方式、证件、合同资料等日常维护不强制走任职审批。请假、加班、报销、出差、采购、通用申请继续使用原有审批。

## 对象关系与维护入口

账号、关联人员同步和权限方案变更共同复核当前审批与办理分工。办理账号即使尚未关联人员档案，也不能直接停用、撤销对应查看／发放／完成权限或关闭模块，留下失效分工。先在“办理分工”中交接人员，再调整账号；共享方案和岗位默认变更复核所有实际继承账号，独立权限账号不受该来源变化影响。拒绝的变更在同一事务回滚，原权限、版本及会话继续有效。

| 对象 | 维护职责 | 联动规则 |
| --- | --- | --- |
| 公司、部门、层级 | 管理员在组织架构维护 | 部门负责人已有的部门范围权限覆盖所管部门及启用子部门；普通成员不因处于上级部门获得下级范围 |
| 人员档案 | 人事维护工号、姓名、实际职位、任职状态、日期和资料 | 员工可没有账号；通讯录与私密档案分别授权 |
| 职位 | 公司维护启用/停用的常用职位目录，人员入职、纠错、调岗、返聘及审批申请可选择或自定义 | 普通员工、总经理、会计等是任职信息；停用目录项不改写历史，不根据名称授予权限 |
| 主职、兼职与矩阵汇报 | 入职、登记纠错、调岗、返聘及其审批表单共用编辑器 | 每人一个主部门，最多 20 个不同兼职部门，各任职有独立职位、直属负责人及最多 10 位职能负责人 |
| 登录账号 | 管理员维护用户名、密码、启停和权限来源 | 普通账号可先建后关联；员工与账号最多一对一 |
| 角色、共享分组、独立权限 | 管理员在账号与权限维护 | 决定模块、操作和数据范围；不根据职位或负责人身份自动提权 |
| 部门负责人 | 组织架构选择在职人员 | 部门链审批要求关联启用账号且具有对应审批权限 |
| 公司执行负责人（CEO） | 公司信息选择在职人员 | 要求启用关联账号拥有公司范围的全部人事、行政及会议室/物品申请查看和审批权限；与部门树独立 |
| 审批人、代理人、办理人 | 管理员配置审批规则、代理和办理分工 | 决策与交付分开；办理分工不授予审批权限 |

推荐开通顺序：公司、部门与职位目录 → 人员档案、任职与汇报关系 → 普通账号与权限方案 → 关联人员账号 → 公司执行负责人、部门负责人及办理分工 → 配置审批阶段、条件与可见性 → 按需开启人员变动审批。

### 总经理、部门主管和兼任人员如何配置

成熟的人事/协作系统通常分别记录人员、任职、组织、登录身份、操作权限和流程责任，参考见文末 Frappe HR/ERPNext 文档。职位对通讯录、任职历史和管理识别很重要，但名称会随公司变化，同名职位的职责也可能不同，因此不能把“总经理”字符串解释为系统管理员或全部数据权限。

组织树的节点是公司和实际部门。通常直接建立“公司 → 财务部、外贸部、单证综合部”，在公司信息中将总经理设为**公司执行负责人（CEO）**；无需为这个人虚构同名部门。实际存在总经办时可正常建部门。部门树表达组织隶属，人员的主职/兼职及直属/职能汇报独立维护，避免用一个树同时表达所有管理关系。审批可配置“申请部门负责人 → 公司执行负责人”或“直属负责人 → 职能负责人会签 → CEO”。

在“账号与权限 → 权限方案”选择**新建方案起点**，再点击“新建方案”，核对并保存：

| 人员实际职责 | 推荐权限起点 | 需另外配置 |
| --- | --- | --- |
| 普通员工 | 普通员工方案或角色默认 | 所属公司、部门、人员关联 |
| 部门主管 | 部门审批负责人 | 关联在职人员并在组织架构指定为负责人；部门范围含任职部门、所管部门及其启用子部门，审批仍须对应动作和流程 |
| 总经理、跨部门审批负责人 | 公司审批负责人 | 保持全部人事、行政及会议室/物品申请的公司级查看/审批模块开放，关联人员后设置公司执行负责人 |
| 人事专员 | 人事管理员角色或其自定义共享方案 | 私密档案与任职办理范围、需要审批的人员变动 |
| 人事、行政、财务、外贸等兼任 | 组合多个职责方案 | 核对数据范围、关闭模块及审批与办理分工 |

部门/公司审批起点复制当前内置普通员工方案的可授权操作及关闭模块，再给具有审批动作的人事/行政资源增加相应范围的“查看”和“审批”。它不会自动保存、分配给账号或改变现有人员权限；请核对被关闭的模块及管理员曾修改的普通员工起点。普通员工原有的新建、编辑仍保留本人范围。默认普通员工起点不会增加私密人事档案、账号管理、财务接收、资源发放或他人资料编辑。共享方案可以改名为“总经理审批”“外贸部主管”等公司用语。

总经理账号的**角色可选普通员工，权限方案选择已保存的公司审批负责人方案**。选定共享方案后以该方案为唯一权限来源，角色只作为未选方案时的默认值，不叠加两套授权。多个不同职位可复用同一方案，同一职位也可使用不同方案。兼任职责在同一方案中组合；当前每个账号使用一个共享方案或一份独立配置，没有多分组叠加。

例如一人兼任人事和行政：选择“组合多个职责方案”，勾选“人事管理员”和“行政管理员”，点击“新建方案”，命名为“人事行政综合岗”，核对后保存，再把账号的权限方案设为该方案。需要财务或业务职责时也可加入对应来源。相同操作取较大的数据范围；任一来源显式关闭的模块继续关闭，可在新草稿中按需要开放。系统管理员身份不能作为组合来源，技术依赖由服务端计算。组合是来源当前配置的快照，保存后独立维护，修改原方案不会自动改变组合方案；所有使用组合方案的账号则共同跟随它的后续修改。

“查看与审批”快捷设置只选择这两个动作，初始采用部门范围，已有公司/全部范围继续保留；不勾选新建、编辑、办结或财务接收。需要跨部门审批时同时将查看、审批设为公司范围。指定审批人只有本人范围时，保存规则返回校验错误，因为不能审批同事申请。模块、数据范围、当前步骤和有效代理会在办理时再次检查；职位或部门负责人身份本身不能绕过这些检查。

账号或方案可启用**仅查看本人及分派的 OA 申请**。开启后，普通数据范围内还必须满足本人申请、明确审批分派、有效代理或明确办理分工；列表计数/分页、详情、附件、历史、通知及待办共同执行。该限制不授予操作权限，也不扩大原有公司/部门范围。继承方案的限制不能在账号上取消，组合方案只要任一来源启用就继续启用。使用单步权限池时未明确分派给某人的申请不会对受限账号开放，须使用指定人或配置阶段。人员变动申请可见不等于私密人员档案可见；公司执行负责人不得启用这项限制。

公司职位目录最多 200 项，是常用任职名称目录；仍允许录入目录外职位。人员汇报关系拒绝自我汇报、跨公司、重复兼职部门与循环。部门数据范围包含全部有效任职部门，新增/移除兼职事务同步关联账号并撤销旧会话；职位变化本身不增加任何操作权限。岗位编制数量、职级薪酬、跨公司兼任和未来日期自动生效不属于当前实现。

档案详情的“任职与汇报关系”显示兼职部门名称、兼职职位、直属及职能负责人；无兼职时明确显示未登记。修正原登记错误时，进入“编辑档案”，勾选“纠正登记信息”，展开“兼职与汇报关系”并填写纠错原因后保存；普通档案编辑保留这些关系。实际任职变动使用“办理调岗”或“申请调岗”，可在主部门不变时单独调整兼职和汇报。两条路径保留版本、交接、同公司和循环校验。

仅勾选纠错或展开分区不构成档案修改；关闭可直接返回。实际编辑或移除关系后关闭，会提示取消或放弃，取消保留当前草稿。确认窗口统一挂载到页面顶层，避免被底层弹窗的不可交互状态锁住。

负责范围按当前组织关系计算：例如外贸部负责人持有部门范围查看/审批时，可以访问外贸部和其下属业务组的相应数据。移走子部门或撤换负责人后，后续请求立即重新判定；不缓存到账号任职记录。范围扩大不增加编辑、私密档案、财务接收或系统管理动作，也不跳过审批阶段和仅分派可见限制。跨公司、兄弟部门及普通成员的下级范围继续隔离。

系统管理员是独立管理身份，不绑定人员档案；可管理普通账号和全部人员资料，包括离职档案，也可直接办理其他公司员工的任职变动。详情中的部门选项来自员工所在公司，变动历史保留原公司归属；人员审批仍由所属公司的账号发起。管理员仍遵守一对一、同公司关联、唯一编号、版本和交接约束，避免破坏历史归属。最后一个启用管理员不可删除或停用。

### 双向显示与身份

账号页显示员工工号、职位、任职状态并链接档案；人员页显示账号当前启停状态并链接账号管理。姓名和部门以档案为准，在人事入口修改并事务同步账号；账号页管理密码与权限。管理员可从账号页打开档案纠错，避免两套姓名/组织相互覆盖。

登录信息向本人提供必要的人员摘要，团队申请显示本人工号、部门和职位，不返回身份证、私人联系方式或附件。普通团队申请必须关联本公司在职人员，不能传入其他人员编号代申请；人事变动则由获授权的人事替目标员工提出，目标员工与提交账号分别显示。

姓名允许重复；稳定的人员编号、账号编号用于关联和授权，姓名不用于身份判等。工号全系统唯一，登录名按 NFC、首尾空白和大小写规范化后唯一。人员选择器显示姓名、工号、部门和职位，历史单据保留原人员和申请账号。旧记录缺少工号快照时显示原人员编号，不按姓名猜测。

账号停用不等于离职。更换账号必须先解除当前绑定，再选择新账号；解绑及部门同步继续核对人员、原账号和候选账号未结事项。离职档案可关联同公司普通账号，但账号保持停用。新员工应建立新身份，不复用其他人的人员编号。停用部门前须处理启用下级、负责人、在职人员与启用账号。

管理员打开已有绑定的人员档案，可点击“解除账号绑定”，填写原因后确认。未结申请、审批或办理职责须先交接；提交同时核对人员、当前账号与两者版本，冲突时刷新后重试。解除保留人员档案、账号及历史，账号启停和权限不变，现有登录失效后须重新登录；可重新关联账号。人员“任职与操作记录”保留原账号及解除原因，账号页同步显示未关联。已有绑定历史的档案仍受删除保护，解除绑定不能绕过历史保留要求。

已有绑定时再点击“关联账号”，窗口只显示当前账号、姓名与启停状态，并提供“解除账号绑定”，不加载候选账号或允许直接替换。解绑成功后重新打开“关联账号”才显示选择列表；服务端同样拒绝未经解绑直接更换账号，避免旧页面或并发请求绕过该流程。

## 人员变动闭环

管理员从“申请与审批 → 审批规则与代理”分别选择须审批的人员变动。页面按策略显示“办理”或“申请”；管理员始终保留直接办理入口。启用审批但账号缺少申请权限时明确提示配置权限，后台同时阻止直接绕过。

| 变动 | 生效结果 | 账号与历史 |
| --- | --- | --- |
| 入职 | 建立正式或试用档案，可同时设置主职、兼职及汇报关系 | 不自动创建账号；同一请求重试不重复建档 |
| 转正 | 试用转正式，记录转正日 | 保留工号、账号及权限 |
| 调岗 | 更新主职、兼职、职位及直属/职能汇报关系 | 同步账号任职部门并使旧会话失效，不改变权限角色/方案 |
| 离职 | 核对申请、审批、会议、借用品和办理分工，移交负责人职责后归档 | 停用关联账号、使旧会话失效，保留历史 |
| 重新入职 | 沿用原人员身份，建立新一轮任职 | 默认清空旧兼职/汇报及上一轮转正/离职/试用截止/合同截止日期；账号仍停用，由管理员复核启用 |

直接办理立即生效，生效日不得早于上次变动或晚于公司业务日期，不提供未来自动执行。登记纠错须显式勾选并说明原因；普通人事仅可纠正尚未使用且未开启人员审批的初始记录，管理员可纠正有历史的登记信息。纠正部门/职位仍需交接；离职状态不会因编辑表单变回在职。

审批路径为草稿 → 核对资料/附件 → 提交 → 审批。草稿、驳回、撤回、取消均不改变正式档案。最后一步通过，在同一事务内完成任职变更、账号同步、历史、申请完成及通知，无需再点“完成登记”。生效后不提供作废回滚，应办理下一项变动或由管理员纠错。

申请人和被变动人员的关联账号均不能审批该人员变动，Full SQLite 测试模式也执行。提交和批准复核申请人的当前授权、目标版本、公司、日期和状态；调岗/离职最后生效时再次核对交接。档案已被修改时返回版本冲突并保留待审批状态，撤回更新后重提，不能用旧快照覆盖新资料。两条路径共用任职校验和账号同步。

## 模块、操作和数据权限

权限来源按以下顺序择一，不叠加多份方案：

1. 账号独立配置：完全替代角色/分组，空数组明确没有业务权限。
2. 指定共享分组：跟随分组；不存在或停用时拒绝业务访问。
3. 角色默认：读取同名内置分组。未编辑的系统种子版本 1 使用当前契约默认；管理员保存后采用其选择，自定义和独立配置不被新版默认覆盖。

继承分组时可额外关闭账号模块，无需切换为独立配置；分组已关闭的模块不能由继承账号重新打开。切换来源或普通业务角色保留账号关闭项，重新开放只恢复原有授权；系统管理员仍使用固定身份权限。模块开关同时控制入口与服务端能力；操作权限控制查看、详情、新建、编辑、审批、完成、导出等；数据范围控制本人、部门、公司或全部记录。隐藏按钮不能替代接口授权，关闭模块不删除数据。

档案和通讯录共享模块开关，但通讯录查看不授予私密详情。Full 普通员工默认开放通讯录、本人日常申请、公告通知和个人付款报销打印；不开放私密档案或人员管理。PersonnelManager 默认具有人事办理及人员变动申请/审批能力，已编辑的旧分组需管理员按制度补授新模块。

账号或继承分组更新使相关旧会话失效，写事务重新读取授权；独立账号不受无关分组修改影响。管理员可管理本产品开放的全部能力，不能开启产品版本未提供的功能。导航规则见[导航与页面简化说明](./导航与页面简化说明.md)。

## 人事与行政功能

| 业务 | 已有流程 | 办结含义及边界 |
| --- | --- | --- |
| 档案/通讯录 | 任职、合同/试用到期提醒、证件、文档、账号、历史、交接 | 不自动转正/离职；通讯录只公开工作联系信息 |
| 请假 | 日期/半天、附件、审批、销假归档 | 自然日计算，不含余额、排班或考勤结算 |
| 加班 | 含时区时段、审批、结束后确认 | 每次 15 分钟至 24 小时，不计算工资/调休 |
| 出差 | 行程、审批、返程归档 | 报销另按凭证申请 |
| 费用报销 | 精确金额明细、凭证、审批、财务接收说明 | 已移交财务不代表付款，不生成会计分录 |
| 采购申请 | 需求、数量、预算、审批、采购/验收说明 | 按实收数量另行入库并记录采购编号，无采购订单/自动入库 |
| 通用申请 | 用印、证明、IT、维修等事项、审批、指定人办结 | 用印和证明须选具体事项，记录实际交付 |
| 会议室 | 冲突检查、申请、单步资源审批、场地/钥匙交接、归还 | 每间会议室指定办理分工，在途预约阻止停用/更换分工编号 |
| 消耗品/借用品 | 申请、审批预留、发放；借用品分次归还 | 消耗品发放即结束，有历史后不能改单位/归还类型 |
| 公告 | 草稿、发布、撤回、归档、受众、附件、阅读确认 | 发布版本与回执保留，打开页面不自动确认 |
| 通知/待办 | 提交、获批、驳回、催办、交接、办结、分工变更提醒 | 已读不完成业务，业务入口复核当前授权 |

财务默认只能接收授权范围内已批准/已移交的报销，不能读取他人草稿；行政管理不自动获得私密人事权限。客户、供应商、商机、单证和付款打印继续独立授权。没有实现薪酬、考勤、总账、支付、采购订单或 WMS，不以同名页面声称完整 ERP 等价。

办理分工支持 1–10 人，任意一人完成当前操作即可，记录实际操作人、时间、说明与版本，同一旧版本只能成功一次。会议开始/结束、借用品发放/归还是不同操作，可由不同指定人员完成。接任修改原分工人员，未结事项交接并通知；旧人员不能借旧通知越权，已有快照和历史保留。

### 审批、附件与历史

六类日常 OA 和人员变动复用同一审批引擎，支持单步权限池、指定人依次审批、部门负责人逐级审批，以及最多 10 阶段、总计最多 50 位审批人的配置流程。每阶段可选择指定账号、申请部门负责人、任职直属负责人、全部职能负责人或公司执行负责人。同阶段全员会签，全部通过后推进下一阶段；任一人驳回即结束，不能越级或重复签署。旧无阶段字段的已提交快照继续按原顺序串行。

报销、采购可按明确币种与精确十进制金额选择条件流程；区间下限包含、上限不包含，同币种区间不得重叠，不匹配时走默认流程。提交时解析任职和组织源，保存规则版本、命中条件与具体审批人快照，之后设置变更不重写在途步骤。日常申请创建时可选择本人有效主职/兼职部门，保存后不能更换；入职审批取拟入职部门，其他人员变动取当前部门。审批人办理时仍须有当前权限和数据范围。

管理员可从申请详情**移交未完成审批**，指定原审批人、接任审批人及原因，核对当前版本和接任资格；仅替换 Waiting 步骤，保留已签意见与实际操作人，记录移交历史并通知。削减账号/方案权限、停用或调整部门若会破坏在途审批或 CEO 职责，整个事务拒绝并回滚，须先交接。离职、解绑还需交接公司执行负责人、部门负责人以及别人对自己的直属/职能汇报关系。

代理不递归，同一人不能代批多个步骤；人员变动排除目标员工账号。申请人每份待审批申请每小时可手动催办一次。当前没有任意加签、或签、后台自动升级/催办、短信或即时聊天。会议室/物品保留单步资源审批；CEO 的公司审批方案包含资源审批，但不自动授予资源发放、财务接收或私密档案权限，确需兼任时在方案中另授相应操作。

日常 OA 全部批准后进入待完成/财务接收，人员变动全部批准后立即生效并完成。待审批内容和附件冻结，修改先撤回；请假/出差和加班的已完成时段仍参与同人重叠校验。金额用十进制字符串及 Rust Decimal，明细最多 100 行，日期使用严格自然日或带时区时间点。

人员、OA、公告复用附件队列：单文件最多 10 MiB，单记录最多 20 个/50 MiB，支持 PDF、PNG、JPEG、DOC/DOCX、XLS/XLSX；头像和证件单图最多 5 MiB。校验实际类型、容量和摘要，Office 容器有界读取并拒绝损坏、伪装或宏项目。只保存/下载原文件，不执行宏或导入业务数据。

先保存记录，再依最新版本顺序上传；部分失败保留成功项，重试继续剩余文件。附件存于当前数据库并随备份恢复，无新增上传目录或匿名地址。普通人事不能直接修改离职资料，管理员可纠错。详情、历史、附件、通知和列表一致校验公司与当前权限。

事件保留操作人、时间、原因和版本，历史引用阻止误删；OA 不提供硬删除。未发布公告草稿可有原因删除，发布过的公告只归档；正文/附件修改须撤回，重新发布保留旧回执而不替新版本确认。通知与业务事件同事务去重保存，前台定期刷新，已读不完成审批。

## 分层与部署边界

正式多人行政场景属于 Full Web/Docker + PostgreSQL 18，单 API 实例、有界连接池。Full SQLite 便携包用于本地界面和登记测试，日常申请允许操作员选择人员登记；人员变动仍禁止申请人与目标员工自批。Document/Sales 桌面不开放行政人事，Administration 不单独打包。

React 表单、hook、模型和生成客户端分责。Domain 的 personnel_organization/approval_policy 负责纯关系和条件规则；Engine 的 personnel_organization 负责关系校验与投影，oa::approval_routing/approval_handover 负责流程解析和移交，oa::personnel_changes 管理任职生效，personnel 管理账号同步/历史。handling 管理分工/授权，office_workflows 管理资源交接/库存，communication 和 worklist 管理通知/待办，Storage 负责两种数据库的一致过滤，不建立第二套审批引擎。

沿用既有 records/files、审计和备份，不增表、不增依赖。人员审批为 oa-personnel，策略保存在公司 OA 设置；旧六类设置读取时补齐人员规则且默认不强制审批，读取不改写配置。API 与两端客户端从同一 OpenAPI 生成。

人员、OA、历史和通知在存储层过滤分页；会议室/物品目录与申请同样在 Storage 执行公司、范围、分工和筛选后计数分页，本页再补齐办理人员及会议室使用状态。只读请求不取得写入协调锁，交接定向读取相关资源申请；办理、审批和库存写入仍使用原事务。Windows Tauri、其它 OS/架构和实际 PostgreSQL 部署各自验收，不将本地测试视为全部平台完成。
