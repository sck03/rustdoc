# 行政办公、人事管理与申请审批

> 2026-09-25：本文描述 Rust 应用的模块和操作边界。历史 C# 表结构、测试与独立产品包裁剪不作为当前验收证据。部署和数据库以[当前架构事实](./当前架构事实.md)为准。

## 导航与职责

| 导航 | 页面 |
| --- | --- |
| 工作台 | 我的待办、申请与审批、工作概览、文件任务 |
| 人事管理 | 人员档案、公司通讯录、员工请假、加班申请 |
| 行政办公 | 会议室预约、物品领用、费用报销、出差申请、采购申请、通用申请 |

请假属于人事与 OA 审批的交叉范围。报销的提交和审批属于内部协作，记账、付款和总账通常属于 ERP 财务。本项目已有独立财务软件，因此新功能只管理申请、附件、审批和移交：报销最终状态为“已移交财务”，不产生原付款记录、不套用付款报销模板，也不执行付款或会计记账。

采购功能管理需求、数量、预算和验收记录，不建立采购订单、应付账款或第二套仓储系统。物品领用继续使用既有库存、预留、发放和归还流程。此次不包含薪资、考勤打卡、排班、法定假期计算和假期余额扣减。

## 六类申请

| 类型 | 专用内容 | 批准后的处理 |
| --- | --- | --- |
| 请假 | 假别、开始/结束日期、上午/下午、事由 | 时段结束后销假归档；时长按自然日、半天计算 |
| 加班 | 包含时区的开始/结束时间、地点、事由 | 时段结束后确认完成；每次 15 分钟至 24 小时 |
| 费用报销 | 币种、费用类别、发生日期、逐项说明和金额、凭证 | 记录移交对象或独立财务软件接收编号 |
| 出差 | 目的地、出发/返程日期、事由 | 返程后登记完成 |
| 采购 | 品名、规格、数量、单位、预算单价 | 记录采购和验收结果；不自动影响物品库存 |
| 通用 | 用印、证明开具、IT 支持、维修、其他事项 | 记录交付内容并办结 |

金额以十进制字符串传输，用 Rust Decimal 计算，不用浮点数。费用明细与采购明细各最多 100 行；采购逐项乘算并四舍五入到分后合计。日期使用严格自然日类型，加班使用 RFC 3339 时间点，界面按公司的业务时区转换。

先保存草稿，再上传附件和提交。待审批期间内容和附件冻结；需要补充时撤回为草稿。驳回后可编辑并重新提交。批准后只能登记完成或由有审批权的人员作废，不能直接修改已批准内容。取消、撤回、驳回、作废、完成和移交须写明原因或办理结果。团队模式禁止本人审批本人申请。

人员、状态、版本和重叠校验都在同一事务中复核。请假与出差互相检查待审批/已批准时段，加班检查同类重叠。相同请求编号和相同内容返回原申请，编号被用于不同内容时拒绝；并发审批只有一次成功，过期界面返回 409 并保留草稿。

## 附件和历史

六类申请均可上传 PDF、PNG、JPEG；每个文件最多 10 MiB，每份申请最多 20 个、总计 50 MiB。费用报销提交前至少上传一个凭证。服务端校验文件名、实际类型、扩展名和容量，图片执行有界解码，附件按摘要检查重复和下载完整性。

附件元数据和二进制分别进入当前数据库的 `records` / `files`，随现有备份恢复；不写用户临时路径、不新增上传目录或匿名公开地址。下载和删除先校验所属申请、公司和当前权限；知道附件编号不构成访问权限。下载保留原文件，PDF 以附件方式返回。

办理事件使用独立 `oa-event` 记录，保留操作人快照、时间、原因和申请版本，按页读取。修改申请不会覆盖先前的审批记录。申请不提供硬删除入口，人员、账号、公司与部门的历史引用会阻止误删。

## 账号、权限与人员交接

- 每类申请有独立资源权限：查看、新建、编辑与提交、取消、审批与作废、完成登记；报销的完成动作显示为“移交财务”。账号和权限方案界面使用同一生成目录，不维护第二套权限表。
- 公司员工及原有业务岗位默认获得本人申请能力。行政管理员审批本公司行政申请，人事管理员审批本公司请假/加班。行政管理员不会因此获得私密人事档案权限。
- 本人、部门、公司范围在数据库查询前应用；列表、详情、事件和附件一致。管理员和“全部”范围也不能越过新 OA 的公司边界。修改前在事务内重新读取当前账号和权限方案，停用/变更权限不能用旧界面继续写入。
- PostgreSQL 团队申请必须由已关联在职员工的账号本人发起，不能通过传入人员编号代申请。SQLite 单机由操作员选择在职人员登记，界面明确显示“登记批准结果”；记录保留操作人和实际人员。
- 草稿、待审批、驳回待处理、已批准待完成的申请纳入离职和调岗交接。必须先取消、办结或移交，再执行任职变更。已完成历史保留原公司、部门、人员和申请人，不随调岗批量改写。

原有人员档案、账号关联、公司通讯录、会议室和物品流程继续使用既有服务。通讯录不返回身份证和私密人事字段；会议室继续检查预约冲突和钥匙交接；物品继续原子预留、发放与分次归还。

## 分层与存储

`export-doc-domain::oa` 管理日期、金额、时段和状态规则；`engine::oa` 管理申请、授权、事务、附件和事件；`export-doc-storage::RecordQuery` 提供公司/部门/所有者/人员/父记录/状态过滤和数据库分页。React 的 `features/oa` 负责此能力，复用 `features/office` 的员工选择器和基础对话框；模型、客户端适配、查询 hook、表单、详情及路由分开。

空库基线更新为 5。共用当前数据库的 `records`、`files` 和审计表，申请记录分为 `oa-leave`、`oa-overtime`、`oa-expense`、`oa-travel`、`oa-purchase`、`oa-general`，附件/事件有独立记录类型。SQLite 与 PostgreSQL 增加公司分页、人员状态及父记录索引。按未投产约定拒绝旧实验库，不添加猜测迁移、不自动重建已有数据库。

正式团队拓扑仍为单 API 实例加 PostgreSQL 18、多浏览器用户。新 OA 的列表和历史已下推分页；整个项目仍有旧查询在应用层分页和单连接互斥的规模限制，不能据此宣称多 API 高可用。

## 参考与验证

流程参考 Odoo 19 官方文档的[请假](https://www.odoo.com/documentation/19.0/applications/hr/time_off.html)、[费用审批](https://www.odoo.com/documentation/19.0/applications/finance/expenses/approve_expenses.html)与[采购需求](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/purchase/manage_deals/rfq.html)。实际阅读对应官方 documentation 仓库源文档；只借鉴申请、审核、凭证和办结职责，不依赖其产品，也不复制完整 ERP 财务功能。

- `oa_service` 和 `support/oa_contract.rs`：六类申请、精确金额、幂等、重提、撤回、附件冻结、下载回读、并发审批和交接；团队测试复用同一场景。
- `test-native-postgres.ps1`：隔离 PostgreSQL 18、独立业务账号、存储合同、OA 团队流程及灾备；ignored 不计为已通过。
- `cargo build --locked -p export-doc-server --example office_review` 后运行 `npm --prefix apps/export-doc-web run test:oa-ui`：真实 React、生成客户端、Rust HTTP、SQLite 的六类操作，包含中文字段、PDF 上传、办理历史、桌面/手机布局；示例仅监听回环地址并使用显式隔离 DataRoot。
- 导航模型、无障碍、样式、缩放和视觉基线继续走现有检查。Tauri 窗口、其它 OS/架构和真实业务验收分别记录。

本批最终结果记录于[进度](./程序改进重构进度文档.md)。系统级 Authenticode、Developer ID 和 Apple 公证保持关闭；Tauri updater 的签名与公钥信任合同保留。
