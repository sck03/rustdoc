# 2026-11-24 OA 办理责任核对

## 实现与边界

- 请假、加班、出差的默认办理节点分别使用“销假登记”“加班完成确认”“出差归档”；保留稳定编号、依赖关系、Complete 动作和历史发布事实。通用申请继续使用“实际办理登记”。已保存节点可在编辑器中改名，不自动覆盖。
- 责任来源解析在业务错误中补充节点和实际动作。权限名称共用现有目录投影，具名办理人缺权不再引导选择“审批方案”；缺失账号关联、任职、权限或分工仍阻断，不以管理员代替业务办理。
- 原错误状态及诊断分类保留；数据库、文件、超时和取消不包装成责任配置错误。没有新增 API、数据库模型、依赖或权限。
- 销假与加班确认属于对应申请资源的办理权限，可单独授予，不要求私密人员档案权限。人事管理员初始方案包含两项，行政管理员包含出差、采购和行政办理；部门／公司审批方案继续只负责审批。

## 针对性验证

- `cargo fmt --all --check`；Engine `oa_service` 的 `configured_approval_chain_delegation_reminders_and_finance` 通过，覆盖审批、代理及财务、分工交接。其旧夹具补齐独立的人事和财务办理人员，避免依靠维护身份完成业务。
- `test_oa_responsibility_ui.mjs` 通过：真实 Rust HTTP／React、隔离 SQLite，全部 13 种内置定义责任解析；8 类办理流程在有权限但未关联人员时明确报错，关联后返回有效业务身份。覆盖具名审批人缺少销假权限时仍返回 403、消耗品跳过归还、错误在实际仿真弹窗显示与关联后清除。注册到已有 HTTP 夹具构建步骤的 `test:oa-ui`；本地仍可独立运行。
- 前端无障碍契约与脚本套件通过。React 源码、样式和生成契约未改变，无需重复完整前端构建或视觉基线；未运行全工作区 Rust、PostgreSQL、跨平台真机或 PDF 下载专项。
- Windows 桌面截图工具两次返回 `capture factory: 不支持此接口 (0x80004002)`；本批不记录桌面截图验收通过。数据核对使用共用 Rust 应用服务，保留原库快照，临时检查程序不提交。

## 交付与清理

- 当前 Full SQLite 轻量测试包的 Windows locked Debug build 通过，沿用原启动入口和原 DataRoot；本包未携带 OCR，不作为完整 OCR 发布验收。
- 使用正式清理器先盘点，再清理已退出的 Cargo 测试程序与元数据，释放约 179.8 MiB。另盘点结束的隔离数据库与浏览器 profile 约 92.3 MiB；批量与单个精确目录删除均被自动审批以 `blocked by policy` 拒绝，该部分仍保留，未绕过审批。通过的截图、业务数据库、关联前快照、实际程序、资源与有效缓存保留。
- 原测试库的人员关联冲突单独处理：登录账号 0004 未关联人员，而同名同工号人员关联登录账号 0005。程序拒绝新建重复工号，原关联与历史数据保留，需明确改绑或新增另一人员后才能配置办理职责。

## CI 核对

- 初次普通 business 回归没有 Rust HTTP 夹具，因此新专项出现 office_review ENOENT。将登记改到现有 OA 集成套件，复用已建立的编译入口，不给普通前端回归增加重复 Cargo 构建。
- 在逐项审查有界责任模块和独立专项后，更新 native Rust 与 automation 两项累计基线为实际统计 117600／32235；单文件限额、后续 75／150 行增长限额保持原值。新增业务能力按审查记录入账，未通过删减有效业务或压缩格式适配限额。
- 初次依赖治理在安装 Rust 时遇到 static.rust-lang.org 的临时 DNS 解析失败，尚未执行审计；后续提交重新触发校验。
