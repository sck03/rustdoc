# 2026-11-28 提交回执与查询一致性修复

## 实施范围

本批承接项目审查，按用户授权完成已确认缺陷、资源优化、必要测试、文档和定向清理；不执行完整 workspace/跨平台验收，不添加旧程序或旧数据库兼容。

- 恢复点 COMMIT 发布明确标记创建尝试边界。创建后的响应丢失、回读错误或取消，使用最长 15 秒的独立操作范围核对同一份加密提交对象。核验一致才返回已提交；无法核验时返回 `Unknown`、`QueryReceipt` 和恢复点编号，计划保留“提交结果待核对”。成功写入后的既有认证回读直接提供凭据，不再额外读一次同一 COMMIT。
- 文件回收共用独立的 `CollectionProgress`，记录已完成对象数、逻辑字节和失败阶段。物理删除后的 SQL、日志、审计失败及中途取消保留 `PartiallyCommitted`；远端删除响应不明保留 `Unknown`。清理日志和预检入口继续支持幂等续办，逐对象排他和引用检查不变。这里的字节是对象逻辑计数，不作为宿主磁盘实测释放值。
- 正式档案“取回”通过统一票据下载助手解析 API 地址，适配 Tauri 页面 origin 与本机 HTTP 端口不同的情况。
- 恢复点选中编号不再因初次空列表或不在当前页而被清空；共享分页控件用于列表与恢复表单，刷新和翻页保留密码/确认草稿。列表外的选中编号明确显示编号，最终可恢复性仍由服务端完整预检确认；明确不可用的当前行禁止提交。只有恢复点/恢复页签读取目录，计划/位置页和相应刷新不触发目录扫描。
- 灾备任务复用 `useTrackedJob` 和统一任务查询键，支持服务端运行编号、查询重试和停止跟踪；丢失回执期间保持活动状态，不把查询失败当作写操作已结束。
- 恢复点显示目录在原 60 秒期限内复用未变化的认证摘要，只读取新增 COMMIT；配置/根密钥变化或期限届满重新读取。每次仍核对实时提交集合与所有权，删除项立即从列表移除。恢复和导出继续执行完整核验，冷目录仍须读取全部 COMMIT，最多 10,000 项。
- 人员引用统计下沉 Storage，对现有任职/汇报关系聚合，按人员去重，保持单位、在职状态、有效期和主/兼任语义。汇报图按每批 200 条投影构建有效任职图，不再同时保留全部人员 JSON；环路/失效关系约束保持。该算法仍需要完整有效关系图，不宣称内存与人员规模无关。
- 通用 `visit_matching` 在原事务快照内分批消费记录；CRM 删除联系人的关联更新使用该入口。单位统计复用同次公司列表。移除无调用的任务 `ensure_idle` 和 schema 校验转发函数，实际维护锁、schema 校验和历史业务引用继续保留。

SQL 仅位于 Storage，Engine 负责用例与进度，Domain 继续保留纯业务校验。前端使用现有共享控件/样式，无新增断点或设计令牌。API 原生契约、生成文件、schema 19、仓库格式 2 和依赖版本均未变化。
