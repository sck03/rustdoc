# 局域网附件存储选型与接入

核对日期：2026-11-28。范围为可选的局域网设备 B；A 上应用、PostgreSQL 18 与默认本地附件仍可独立运行。

实际安装按[SeaweedFS 局域网存储安装与连接手册](./SeaweedFS局域网存储安装与连接手册.md)操作；本文保留选型依据和验收证据。

## 结论

**SeaweedFS 社区版 4.55 和 RustFS 1.0.7 是两个已验证的候选。** 两者通过同一组真实服务验收，当前附件与恢复功能可直接使用项目已有的 S3 适配器，不需要厂商专用生产代码。部署仍需创建桶、设置专用凭据并在应用中登记地址和策略。两者均为 Apache-2.0，应用不需要链接或打包其实现。

用户进一步明确使用 **E5200 老电脑作为单台附件设备 B**。在这一具体场景下，建议采用 **SeaweedFS 4.55 的 weed mini 模式**：官方将它定位为可用于生产的单节点文件存储，一个进程组织 Master、Volume、Filer、S3；本次官方发行包也通过了保守老 CPU 指令集验证。RustFS 同样通过指令集与 S3 验证，其单节点单盘文档主要面向开发、测试及小型非关键负载，也允许在保留备份的前提下生产使用。两者单机均不能抵御整机损坏，不能将此文档定位差异解释为实测稳定性差异。此推荐依据部署形式、已完成兼容性证据和维护历史，不表示测得了更低的故障率或更高吞吐。本项目的 PostgreSQL 18.7＋真实 S3 冷恢复已经通过；实际 E5200 设备仍需安装及断电验收。

如果 B 本来就要承担办公室共享盘、硬盘管理与备份，**OpenMediaVault + NFS** 也是合理方案：应用通过已登记目录接入。它使用现有目录适配器，实际挂载丢失、只读、身份及断电行为须在部署设备另验。

| 候选 | 对本项目的适配与取舍 | 当前判断 |
| --- | --- | --- |
| SeaweedFS 4.55 社区版 | 官方支持单节点和 S3 条件写、分段上传；数据卷与 Filer 元数据须一起保护。基础存储、应用恢复不要求企业版；官方提及的高级自愈、数据恢复等企业能力不纳入免费方案承诺 | E5200 单机附件场景的建议方案；设备长期运行另验 |
| RustFS 1.0.7 | 独立 S3 服务；当前兼容矩阵覆盖所需对象、列表、分段和条件写。1.0.0 稳定版发布于 2026-09-16，长期稳定性证据仍需积累，不因同为 Rust 就推断更可靠 | 已验证候选，真实 Windows 服务验收通过；设备长期运行另验 |
| Garage | 轻量且适合多点复制；官方已知限制明确不支持安全的条件写／锁。恢复仓库要求 If-None-Match 原子创建，不能降低该要求来适配 | 不作为统一附件＋恢复仓库首选；未实测 |
| OpenMediaVault + NFS | Debian NAS，提供共享与备份管理；A 先挂载，再向应用登记受管目录；目录身份和介质断开保护必须保留 | 已有 NAS 或偏重共享盘管理时评估；未做真实 NFS 验收 |
| 原 MinIO 社区仓库 | 官方 README 明确停止维护，GitHub 状态为 archived。AIStor Free 的免费授权不等同于此处要求的持续维护开源社区项目 | 不作为新的默认部署依赖 |

Ceph 等多节点集群本次不引入：尚无必须跨设备高可用的需求，不为单台 B 增加新的集群和运维依赖。

## E5200 与指令集验收

- 本机核验的 SeaweedFS 4.55 Windows 发行包含 GOAMD64=v1、CGO_ENABLED=0 构建信息；Go 的 amd64 基线要求 x86-64/SSE2，不能仅因缺少 AVX 就判定无法运行。
- 官方 Linux SeaweedFS 4.55 与 RustFS 1.0.7 musl 归档核验 SHA-256 后，在 QEMU 8.2.2 的 Conroe 模型下通过真实启动、12 路条件创建、12 MiB 分段上传与下载摘要、Range 读取。GitHub 手动运行 46136558218 成功；首次 RustFS 探测在初始化完成前收到 503，修正测试就绪等待后通过，不将其记为产品 CPU 缺陷。
- 此项证明测试过的指令路径可以在保守 CPU 模型下运行，**不是 E5200 实机或性能验收**。该设备的内存容量、磁盘健康、网卡及实际安装系统尚未提供；推荐使用支持该处理器的 64 位 Linux。Debian 13 amd64 安装手册说明支持 Intel 64/AMD64 处理器；不套用较新发行版的不同 CPU 基线。
- B 仅承担对象存储；应用、PostgreSQL 和备份加密仍按 A/B/C 职责布置。尚未用同一 E5200 设备比较两者 RSS、长时间负载、断电或大容量恢复，不给出未经测量的并发数与内存保证。
- 建议 B 直接运行已验收的 Linux amd64 二进制并作为系统服务启动。Windows 功能验收不等于旧 Windows 系统支持；Go 1.21 起要求 Windows 10/Server 2016 或更新版本，RustFS 官方也不建议 Windows 用于生产。

## 模块与接入边界

- 前端继续使用文件与存储／备份设置页和生成客户端，权限与业务引用保留在应用和 PostgreSQL。
- 附件字节由现有本地／S3 适配器管理；S3 签名、寻址、分段、摘要验证及恢复仓库都复用现有模块。本次未增加 SeaweedFS/RustFS 专用业务分支或新数据库。
- 选择局域网 IP 地址时使用 **path 寻址**。配置 endpoint、bucket、region、prefix 和专用凭据；不要启用匿名公共桶，不向普通前端下发存储管理员凭据。
- 文件库和恢复仓库使用独立 bucket／权限。B 是在线文件库时，放在同一 B 的另一桶仍属于同一故障域；正式备份宜放 C 或可离线移动盘。C 不构成首次部署和正常业务操作的前置条件。
- 切到 B 后，断网、认证、只读或身份异常明确失败，不静默回退 A。更换 B 使用应用迁移；不能手工改 file_locations 或拷贝部分对象后直接切库。
- 交付固定已验收的精确版本／镜像摘要，升级后重复兼容与恢复验证。不要将 latest 作为可复现部署依据。
- 单台 B 不能提供跨设备高可用；磁盘镜像／复制不能替代独立恢复点与恢复凭证。

建议连接关系：A（应用＋PostgreSQL）通过 S3 访问 B（附件）；应用将数据库、主密钥、模板和附件一起形成加密恢复点，直写独立 C 或离线介质。浏览器仍通过应用的权限和下载接口访问附件。

## 备份、换机和软件更换

**应用恢复点是跨存储软件的主要恢复路径。** 它保存数据库与附件引用的一致视图、主密钥和模板。日常备份页提供可选择复制的恢复仓库编号；编号、恢复凭证、备份服务地址／桶／前缀和独立 S3 访问凭据须在 A 之外保管。恢复凭证不从后端回显。仅有对象桶或数据库单独一份，不能证明能完整恢复业务。

1. A 损坏但 B 完好：隔离旧 A，在独立维护入口验证恢复点，重新签发凭据并接回原文件库；校验 storeId 与每个被引用对象，不重写其它文件。
2. B 损坏或需要换存储软件：选新的 S3 文件库或受管目录，从恢复点重建并验证，完成后切换；可恢复到本地 A，但要有对应空间。
3. B 完好、只更换 SeaweedFS/RustFS：用现有在线文件迁移执行目标核验、复制、摘要检查与发布。保留原库到验收完成；本次已验证双向迁移。
4. SeaweedFS 自身整机恢复：同时保护数据卷、Filer 元数据、Master 状态、配置和凭据。官方原始卷镜像流程要求暂停写入以保证卷与元数据一致；不能只复制 volume 文件或只复制 Filer 数据库。Docker 使用 /data 时应持久化整个所需目录，避免卷在持久盘而默认 Filer 元数据留在容器层。
5. RustFS 自身整机恢复：保护全部配置卷、内部对象元数据、配置及凭据；如启用额外加密，还须保护相应密钥。普通文件管理器复制正在写入的目录不作为本项目已验收备份方式。优先采用上述应用恢复点或停写后的一致性备份。

不启用会自行删除在线对象的 bucket 过期策略；应用已有正式档案保留和受控回收。S3 Object Lock、版本保留及底层存储配额会改变物理删除和空间释放行为，启用前需单独核对，不能把逻辑删除当作已释放磁盘。

### 主设备 A 损坏、原 S3 设备 B 完好

在新 A 安装已验收的同版本程序和 PostgreSQL 18，使用新的 DataRoot／数据库进入独立灾备维护。旧 A 必须停止并隔离，避免重新上线后与新实例同时写入。填写独立备份位置、恢复仓库编号和恢复凭证，解锁恢复点后选择“接回完好的原文件库”，通过完整预检再执行恢复。停止维护服务并启动业务服务后，使用恢复后的账号登录，检查原附件下载并新增一个附件验证读写。

重接会恢复数据库、应用主密钥和文件库配置，并核验原库身份及被引用对象的摘要；保持原 S3 的地址、桶、前缀和身份，不要求先将全部附件复制到新 A。凭据失效或地址变化时使用维护页的“重签 S3 访问凭据（可选）”，仍须指向同一个真实文件库，不能把一个空桶当作原库。权限、网络或库身份不符应修正后重新预检，不应跳过核验。

**能恢复到最近一次成功恢复点的业务状态，不保证恢复点之后的变更。** S3 中仍有某个附件，不代表对应单据、权限和关联记录仍可还原；这些关系保存在 PostgreSQL。若 A 的数据库和全部恢复点都丢失，仅靠附件桶不能完整重建业务。因此至少把应用恢复点及解密／访问凭据保存在 A 之外；若备份与在线附件同在 B，再保留独立介质副本以覆盖 B 的整机损坏。

## 本次真实验收

官方发行归档先核验 SHA-256，再在仓库隔离目录、127.0.0.1 端口运行，无客户数据。使用本项目真实 HTTP、应用服务、文件存储及 SQLite Full 验收程序；不是 S3 mock。两者均完成：

- 12 个并发 If-None-Match: * 请求：1 成功，11 返回 412。
- 存储进程重启后已提交对象仍可读取。
- 本地附件迁入 S3；10 MiB 文件走分段上传；下载 SHA-256 一致及 Range 正确。
- 存储离线时写入返回 503，当前文件库仍为 S3；服务恢复后健康状态恢复。
- SeaweedFS → RustFS → SeaweedFS，以及相反方向的迁移，附件摘要保持一致。
- 加密恢复点直写 S3，含多层前缀的恢复点发现／列表查询。
- 从 S3 恢复点重建本地文件库，重启应用后数据库恢复；附件完整，恢复点之后的数据消失，旧会话失效。

通用脚本另外覆盖真实 PNG 图片。SQLite 记录位于 artifacts/2026-11-28-storage-consistency/external-s3/。随后使用独立 PostgreSQL 18.7 集群、普通 API 账号和仅在维护阶段使用的维护账号，完成了真实 React 冷恢复：

| 恢复来源 | 故障隔离与目标 | 结果 |
| --- | --- | --- |
| SeaweedFS S3 加密恢复点 | 停止源应用，关闭全部旧在线附件 TCP 路由；恢复到全新 PostgreSQL 库、新 DataRoot 和本地附件目录 | 通过 |
| RustFS S3 加密恢复点 | 同样隔离旧实例及附件路由；恢复到全新 PostgreSQL 库、新 DataRoot 和 SeaweedFS 的新对象前缀 | 通过 |
| SeaweedFS S3 加密恢复点 | 只停止旧 A，原 B 保持在线；全新 PostgreSQL 库和 DataRoot 接回原 SeaweedFS 文件库 | 通过 |
| RustFS S3 加密恢复点 | 只停止旧 A，原 B 保持在线；全新 PostgreSQL 库和 DataRoot 接回原 RustFS 文件库 | 通过 |

四个用例均检查备份页的可复制恢复仓库编号，在独立维护页输入错误凭证并确认拒绝，再正确解锁、完整预检、执行恢复、重启普通 API。逐个核对图片与 10 MiB 分段文件的 SHA-256、主密钥、用户模板；核对备份后新增记录不存在、旧登录令牌返回 401，并实际上传恢复后的新附件、下载逐字节比对。两个重接用例另外核对原文件库身份、地址、桶、前缀及受保护凭据保持一致。此次修复的是日常备份页未展示仓库编号，以及验收脚本的异步等待；没有为存储厂商添加业务分支。

最终成功日志为 artifacts/2026-11-28-storage-consistency/pg187-s3-reconnect.log 与 pg187-s3-cold-write-accepted.log；s3-final-modes.json 的 Reconnect、Rebuild 均为退出码 0。四个成功目录分别为 artifacts/postgres-s3-seaweedfs/ae8febc0-da67-4648-ac60-79287a81c409（重接）、artifacts/postgres-s3-rustfs/a19eee60-e26e-445f-8926-0bc78bcbda3e（重接）、artifacts/postgres-s3-seaweedfs/2dff65cb-1b0d-458f-95db-d28c1790b57f（本地重建）和 artifacts/postgres-s3-rustfs/d4378088-e1f0-4173-9393-6f2e8fe35151（新 S3 重建）。精简证据归集于 artifacts/2026-11-28-storage-consistency/retained-test-evidence/s3-final/，保留 s3-result.json、维护请求状态和预检／完成截图；隔离数据库、凭据和生成物不提交。

本次旧附件故障是 TCP 路由隔离，备份桶仍可独立访问；不是物理断电。尚未验收实际 E5200/NAS 的硬盘、TLS 私有证书、磁盘写满、长期负载、多节点故障或 TB 级恢复。PostgreSQL/Docker 生命周期已有独立 CI 证据，不将它与本次 Windows 实进程 S3 组合冒称为同一次设备验收。

## 可复用验收入口

使用 scripts/test_s3_storage_integration.mjs。先构建前端和 office_review 验收程序，启动候选 S3 服务并建立专用附件／备份桶。测试使用全新应用 DataRoot 和随机对象前缀，不使用真实业务桶；不负责安装或管理外部服务，也不自动清空测试桶。

将下面配置保存在 artifacts/ 下的私有 JSON，填写专用测试凭据；targets 可有两个服务，以额外验证双向迁移：

~~~json
{
  "targets": [{
    "name": "seaweedfs-4-55",
    "endpoint": "http://127.0.0.1:19346",
    "region": "us-east-1",
    "bucket": "exportdoc-files-test",
    "backupBucket": "exportdoc-backup-test",
    "accessKeyId": "<isolated-test-access-key>",
    "secret": "<isolated-test-secret>"
  }]
}
~~~

~~~powershell
$env:EXPORTDOC_S3_TEST_ISOLATED = '1'
$env:EXPORTDOC_S3_TEST_CONFIG = 'artifacts/s3-test-config.json'
node scripts/test_s3_storage_integration.mjs
# 使用隔离 PostgreSQL 源库与全新目标库，并切断在线附件连接后冷恢复
pwsh -NoProfile -File scripts/test-native-postgres.ps1 -PostgresBin '<PostgreSQL-18.x/bin>' -Scope ExternalS3
~~~

需要支持 SigV4 的 curl。PostgreSQL 的 ExternalS3 场景要求隔离服务监听 http://127.0.0.1，以便由测试自己的 TCP 代理断开旧在线附件路由；它不控制办公室实际设备。默认构建当前服务端；只有已有当前源码的已验证构建时才使用 -SkipBuild。EXPORTDOC_S3_TEST_SERVER_BINARY 可指定 .codex-runtime 内独立服务器副本，须另记来源与摘要，不能把跳过构建当成新的编译证据。命令失败时不打印携带凭据的命令参数。验收后保存 s3-result.json，并按空间清理规则处理隔离测试桶／目录。

验证“只换 A、B 保持在线”时，在每个测试 target 中增加 `"restoreMode": "Reconnect"`，仍通过 PostgreSQL ExternalS3 入口运行。测试停止源应用、建立全新库和 DataRoot，保持旧 S3 路由在线，真实页面选择重接；断言原文件库身份及连接配置保持不变，并核对恢复后新附件的上传下载。省略该字段则验证旧附件路由断开后的重建场景。

老 CPU 验收通过 browser-compatibility.yml 的 storage_cpu_only=true 手动入口运行，默认浏览器回归范围不变；固定 Linux 归档与校验值在 storage-cpu-compatibility.yml。该运行与 PostgreSQL 冷恢复属于两项独立证据。
