本批从 `6e996f1b` 开始，集中处理分析确认的六类问题。数据库继续只接受 schema 14，依赖版本及产品形态不变，不增加旧版兼容链。

## 实现与边界

- 客户、出口商、收款对象、商品、港口和单位的 DELETE 原生契约明确要求 `rowVersion`；重新生成 OpenAPI、运行契约及 React 客户端，列表和编辑页都传读取时版本。缺少版本或版本过期不能删除，存储并发检查保留。冻结契约逐项声明这六处差异，其余认证、权限、响应及容量元数据继续对照。
- Storage 在人员变更定时查询的 `LIMIT 20` 前筛选当前提交版本、已批准且未暂停的流程。Engine 保留事务内复核；暂停的前 20 项不会饿死后续任务，恢复后重新获得调度资格。
- 审批单生成的准入 429 向调度器返回，保留 Active 节点；本轮停止继续争用，沿用原有调度间隔重试。审批事务不会回滚，真正失败继续进入可观察错误流程。互斥锁损坏映射为 503，不当作临时拥堵。
- 主数据列表按实体建立组件作用域，旧查询占位仅可在同一实体内复用。删除及 HS 批量删除共用 `useScopedSave`，取消、卸载、权限、版本和刷新反馈走同一边界。查询期间鼠标、键盘、选择和确认操作一致禁用，移除批量删除后的重复读取。
- OA、付款、主数据、CRM 客户、装柜及报表历史等已区分写入/刷新结果的调用显式启用 `throwOnError`。成功先接受已提交状态，刷新失败只提示重新读取，避免把成功写入误报为失败。联系人、供应商评价和邮件模板原本直接等待请求的刷新路径经核对保留。
- 发票编辑使用每个编辑器独立的不可变行投影器；未修改行保留引用，文字编辑复用精确合计，数值、币种和汇率变化重新计算。公共规范化函数仍是纯函数，删除全局 JSON 签名缓存和无消费者的复制函数。缓存不持久化，弱引用随草稿生命周期回收。

## 验证

本批新增回归覆盖六类主数据删除的缺少版本、过期版本、成功删除与回读；暂停队列超过一批的反复调度及恢复；两个文件工作槽占满时批准成功、系统节点保持 Active、释放后自动启动审批单；真实 React 分类切换、迟到删除与刷新失败；5000 行不可变投影、精确金额、打印行和撤销等价性。

全量测试另发现 Windows 文件故障夹具在同一路径删除文件后立即创建目录，可能遇到删除尚未完成而失败。改用独立临时目录分别验证损坏目录和非目录根路径，保留原故障断言；没有改变生产文件操作。

PostgreSQL 实库首次运行发现新增调度夹具接在预期外键失败断言之后；PostgreSQL 会中止该事务，导致后续 SQL 返回 `25P02`。将预期失败断言移至事务末尾，再重跑 SQLite 与 PostgreSQL，保留外键保护和调度的全部检查。

复用既有测试入口与夹具。Rust 集成测试/示例范围的审查基线设为 29,746 行，比原基线增加 124 行，主要为六类版本删除及跨数据库调度回归；后续 120 行增长额度与单文件限制不变，生产范围上限未放宽。
