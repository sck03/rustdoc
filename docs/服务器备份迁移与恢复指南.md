# 服务器备份、迁移与恢复指南

> 2026-10-13。适用于 Docker Full 和非容器 Full 网页版，数据库均为 PostgreSQL 18。部署步骤分别见[Docker 指南](./Docker容器部署与启动指南.md)和[网页版指南](./网页版部署与启动指南.md)。

## 1. 先选择正确的备份

**日常至少保存数据库备份；升级、换机和灾难恢复准备完整迁移包，并另外保存部署配置。备份要下载到另一台设备或受保护的离线介质。留在原服务器上的文件，不能防止原服务器磁盘损坏。**

| 文件/内容 | 包含什么 | 适合什么情况 | 不包含什么 |
| --- | --- | --- | --- |
| `.dump` 数据库备份 | 业务库中的单据、账号、设置、图片、附件、模板记录与历史 | 原服务器回退到某个备份时间点 | 文件主密钥、DataRoot/Templates、服务器连接配置 |
| `.edmmigration` 完整迁移包 | PostgreSQL dump + `Security/native-master-key.bin` + `DataRoot/Templates`，密码加密 | 换服务器、Docker 与非容器互迁、整机丢失后的重建 | 程序、数据库角色密码、Docker RuntimeRoot、代理/证书、日志缓存、文件任务输出和交接目录 |
| 部署配置副本 | Docker RuntimeRoot，或网页版连接/初始化口令文件、服务托管及代理配置 | 原部署复原、排查连接与运行参数 | 业务库本身 |
| `.edmrecovery` | SQLite 桌面灾备包 | Tauri 单机桌面恢复 | 不是 PostgreSQL 团队迁移包 |
| `.edpkg` / Excel / PDF | 某些单据或输出内容 | 业务交付和局部数据交换 | 不能恢复完整系统及所有账号/附件 |

界面中的“数据库备份”调用 `pg_dump`，是 PostgreSQL **custom-format 逻辑备份**。旧接口名称中的 PhysicalBackup/“物理备份”不表示它是原始数据库目录，也不是可用于时间点恢复的 WAL 归档。

业务库中的敏感设置和授权安装身份受到主密钥保护。**只有 .dump、没有原主密钥时，不能保证邮件凭据、授权状态等可正常读取。**完整迁移包会带上该密钥；恢复不重置授权有效期，也不绕过许可证校验。

## 2. 每次操作前，记下这张记录

记录实际值并与备份一起保存，密码另放：

| 记录项 | 例子/说明 |
| --- | --- |
| 程序版本和来源提交 | “关于与支持”中的版本、构建标识 |
| 部署方式 | Docker 或非容器网页 |
| 镜像/程序包 | 固定镜像版本/摘要，或 Web 服务压缩包及 SHA-256 |
| 数据位置 | Docker 项目和卷名；或 AppRoot、DataRoot、PostgreSQL 实际数据目录 |
| 配置位置 | 原 RuntimeRoot 或连接文件目录 |
| 备份时间和文件名 | 以下载得到的文件为准，注明公司业务日期/时区 |
| 恢复账号 | 备份时可用的管理员账号；密码另行保管 |
| 迁移包密码 | 放密码管理器或单独安全记录，不与包放在同一个公开目录 |
| 其他资料 | HTTPS 证书、代理配置、任务导出文件、持卡机交接资料 |

创建包前核对磁盘余量。生成、上传、恢复及安全回退会同时保留多份文件，需要明显多于单个备份文件的可用空间。不要用“删除旧库”来给恢复腾空间。

## 3. 日常创建并下载数据库备份

1. 管理员登录网页。
2. 进入“**系统管理 → 系统设置 → 备份与恢复 → 团队库与完整迁移**”。也可从顶部“查找功能”搜索 PostgreSQL。
3. 在“数据库备份”分区操作；需要排查时展开“服务器信息与备份位置”，确认“团队库模式：已配置”“客户端工具：已就绪”。
4. 点击“**创建备份**”，等待完成。时间较长时到“工作台 → 文件任务”查看；失败先查看原因，不把排队提示当作成功。
5. 在下方备份列表找到刚才那份，直接点击该行的“**下载**”。日常下载不必展开恢复表单。
6. 确认浏览器下载完成，文件扩展名为 `.dump`，大小不是 0。把它复制到另一设备/受保护备份介质，并记录时间与版本。
7. 定期按第 7 节演练恢复。只看见文件名或下载成功，还不能证明可恢复。

原服务器文件位于 `DataRoot/Backups/PostgreSQL`；Docker 内对应 `/var/lib/exportdoc/Backups/PostgreSQL`。普通用户无需进入容器或手工找 Docker 卷，直接从网页下载即可。

`.dump` 本身不加密，包含业务和人员资料，应放在加密磁盘/受控备份存储。普通 ZIP 压缩不能代替加密。

**当前 Rust 版本尚未执行界面历史配置中的定时备份、保留份数或自动删除。**“计划与保留”只展示历史参数，不能当作自动备份已经运行。安排明确的人工备份责任人，或由服务器管理员另行设置并验证运维备份任务。当前 WebDAV 路径针对 SQLite 备份，不替代 PostgreSQL 服务器备份。

## 4. 创建完整迁移包

1. 仍在“团队库与完整迁移”，展开“**完整迁移与换机**”，找到“完整迁移”表单。
2. 填写“管理员当前密码”，这是当前登录系统的管理员密码，不是 PostgreSQL 密码。
3. 设置“新迁移包密码”并再次输入。网页创建要求 12–128 字符，包含大小写字母、数字和符号；请先安全记下。
4. 在“创建确认文本”中输入 **`MIGRATE`**，点击“**创建并下载迁移包**”。
5. 等待后台任务及浏览器下载完成，取得 `.edmmigration`。单独保管包密码；遗忘后无法解密。
6. 另存第 2 节的部署配置、原程序包和需要保留的外部资料。

已有合法包恢复时使用它原来的密码，不要求改成新密码规则。上传后的密码错误会拒绝暂存，不修改业务库；修正密码后可以重新办理。

迁移包总展开内容上限为 256 MiB，浏览器请求/下载也有独立的 256 MiB 边界；不是无限容量备份工具。文件压缩、解压和摘要校验采用分块处理，密封加解密仍使用有上限的内存缓冲。超过范围时由数据库管理员使用 PostgreSQL 原生离线备份方案，配套保存主密钥和用户模板，并在隔离目标验证。不要把包拆分、修改清单或手工改 schema 标记后强行导入。

如果部署使用 `EXPORTDOCMANAGER_MASTER_KEY` 环境主密钥，程序拒绝生成/恢复独立文件密钥包。由管理员按该部署原有密钥保管方式迁移，不可删除密钥环境变量后试运行来“修复”。

## 5. 原服务器：恢复一份 .dump

这会把**整个业务数据库**回到备份时的状态，不是把新旧资料合并。备份之后的新单据、账号、权限修改等会被回退。

### 5.1 先准备

1. 通知所有使用者停止录入，等待重要文件任务结束；需要的输出先下载。
2. 为当前状态另建一份完整迁移包并下载，防止选错备份。
3. 确认仍保留匹配的 DataRoot、主密钥、用户文件模板与服务器配置。缺少这些时优先使用完整迁移包。

### 5.2 在网页安排恢复

先展开“**恢复数据库（回到某份备份）**”，在其中的“数据库恢复”分区：

- 原服务器已经有备份：在下拉框中选择目标文件。
- 备份保存在自己电脑：点击“选择 .dump 文件”，选择以前下载的文件。

然后填写“管理员当前密码”，在“恢复确认文本”输入 **`RESTORE DATABASE`**。根据所选来源点击“**恢复所选备份**”或“**恢复上传文件**”。

看到“恢复已暂存”说明文件检查和安排已经完成，**数据库还没有恢复**。页面会自动展开“下一步：请部署管理员完成恢复”，显示 Linux Docker 的维护命令和详细手册入口。该状态会阻止继续安排另一份恢复；下面由服务器管理员完成停机维护。

### 5.3 Docker 执行恢复

在原源码根目录打开 PowerShell 7，重新设置实际使用的参数：

```powershell
$run = @{
    RuntimeRoot = '/srv/exportdoc/runtime'   # 使用原目录；Windows 改成原 E:\... 路径
    Image = 'exportdoc-rust-native:local'     # 发布部署改成原来的固定镜像
    BindAddress = '127.0.0.1'                # 保持原绑定地址
    Port = 5188
    NoPause = $true
}
./scripts/run-native-docker.ps1 @run -RestorePending
```

脚本会先准备镜像、停应用、等数据库，再运行恢复容器；成功后启动应用。不要先换 RuntimeRoot，不要额外运行初始化容器，更不要删除卷。出现错误时应用保持停止，按第 9 节排查。

### 5.4 非容器 Windows 执行恢复

先在原服务终端 Ctrl+C 并等待退出。新开 PowerShell 7，设置原目录：

```powershell
$app = 'E:\ExportDoc\Web\App'
$data = 'E:\ExportDoc\Web\Data'
$runtime = 'E:\ExportDoc\Web\Runtime'
$server = Join-Path $app 'ExportDocManager.Server.exe'
$env:EXPORTDOCMANAGER_POSTGRES_CONNECTION_FILE = Join-Path $runtime 'app-connection.txt'
$env:EXPORTDOCMANAGER_POSTGRES_MAINTENANCE_CONNECTION_FILE = Join-Path $runtime 'maintenance-connection.txt'
$env:EXPORTDOCMANAGER_POSTGRES_OWNER = 'exportdoc_owner'
try {
    & $server --app-root $app --data-root $data --restore-pending
    if ($LASTEXITCODE -ne 0) { throw '恢复失败，保留现场，暂勿启动业务服务。' }
} finally {
    $env:EXPORTDOCMANAGER_POSTGRES_MAINTENANCE_CONNECTION_FILE = $null
}
```

退出码为 0 后，按[网页版日常启动](./网页版部署与启动指南.md#5-windows初始化启动停止)重新启动。不要省略业务连接：维护命令需要核对两个连接指向同一数据库，并恢复业务角色的必要权限。

### 5.5 非容器 Linux 执行恢复

```bash
sudo systemctl stop exportdoc
sudo -u exportdoc env \
  EXPORTDOCMANAGER_POSTGRES_CONNECTION_FILE=/srv/exportdoc/runtime/app-connection.txt \
  EXPORTDOCMANAGER_POSTGRES_MAINTENANCE_CONNECTION_FILE=/srv/exportdoc/runtime/maintenance-connection.txt \
  EXPORTDOCMANAGER_POSTGRES_OWNER=exportdoc_owner \
  /srv/exportdoc/app/ExportDocManager.Server \
  --app-root /srv/exportdoc/app --data-root /srv/exportdoc/data --restore-pending
```

确认上一条命令成功（`echo $?` 为 0）后才执行：

```bash
sudo systemctl start exportdoc
sudo systemctl status exportdoc --no-pager
curl --fail http://127.0.0.1:5188/readyz
```

前台部署先 Ctrl+C 停止原服务，维护完成后按原前台命令启动。

## 6. 换服务器、整机损坏或 Docker/网页版互迁

只要两端均是受支持的 Rust PostgreSQL 18 部署，可使用完整迁移包。SQLite 桌面库、旧 C# 数据库和 PostgreSQL 原始数据目录不走这一流程。

### 6.1 旧服务器还可用

1. 在新机器先部署相同版本或支持该备份 schema 的较新程序，建立全新的 PostgreSQL 数据库和独立配置。不要让新旧 API 指向同一个库。
2. 只让管理员访问新站点，先用新站点的初始化口令建立临时管理员，确认启动正常。
3. 正式切换前，旧站点停止大家录入，完成重要后台任务，创建**最后一份完整迁移包**并下载。
4. 备份旧部署配置和外部资料，停旧应用，保留旧数据和备份，不再继续录入。
5. 在新站点展开“完整迁移与换机”，选择旧 `.edmmigration`，输入**新站点当前管理员密码**、迁移包原密码和确认文本 **`MIGRATE`**，点击“安排完整迁移”。
6. 看到“恢复已暂存”后，对**新站点**执行第 5 节对应的 `-RestorePending` / `--restore-pending`。
7. 恢复成功后使用**旧备份中的账号密码**登录。目标数据库中的临时账号已被旧备份替换。
8. 按第 7 节验收，再切换公司访问地址或 DNS。另行配置 HTTPS、服务自启和外部资料路径。
9. 保留旧站点与最后备份一段约定时间，但不要让两边同时接收新的业务录入。

新机使用新机自己的数据库角色密码与连接文件。迁移包不携带数据库登录角色，也不要求把旧连接文件覆盖到新机；程序恢复后会授予新机业务角色必要权限。原部署原地修复则继续使用原 RuntimeRoot，不能重新生成密码。

### 6.2 旧机器已经无法启动

如果有 `.edmmigration` 和包密码：从上面的第 1、2、5–9 步开始。新机器不需要先启动损坏的旧业务库。

如果只有 `.dump`：还需要原来的 `Security/native-master-key.bin` 和对应用户文件模板。请管理员先在隔离环境准备完整恢复材料，不要把刚生成的新密钥当作旧密钥使用。

如果只有 Docker 镜像、程序压缩包、源码或导出的 PDF：它们不能重建完整业务数据库。保留故障磁盘和现有资料，先做数据恢复评估，不要反复初始化覆盖现场。

## 7. 恢复后逐项检查

由熟悉业务的人核对以下内容后再恢复大家使用：

1. 服务已就绪，版本与计划一致，数据库为 PostgreSQL；日志没有持续恢复/权限错误。
2. 旧管理员及一个普通员工可以登录；公司、部门、人员关联及岗位权限正确。
3. 抽查最近和较早的发票、付款单、OA 申请、公告及历史。确认数据时间点与备份一致。
4. 下载一份原附件，核对大小/内容；打开含印章或唛头图片的单据。
5. 打开私人/共享模板和用户文件模板，生成一份 PDF，检查中文、图片和金额。
6. 检查邮件等敏感设置的“已保存”状态；只有明确需要时才发实际测试邮件。
7. 查看授权状态、待办及文件任务。原任务输出不在完整包承诺内，需要的输出应另存或重新生成。
8. 记录恢复开始/结束时间、使用的备份、检查人和结果。做一次新的完整备份。

演练使用隔离目标和匿名/受控备份，不直接覆盖正在使用的生产库。一次本机成功不能代替所有服务器、磁盘故障和所有数据规模的验证。

## 8. 升级、回退和备份保留

- 当前 Rust schema 为 7，支持从版本 5 起有序升级；旧于 5、未知/损坏、或比程序新的库会被拒绝。不要修改版本标记冒充升级。
- 恢复较旧的受支持备份后，维护命令会升级 schema 并恢复业务角色权限。程序版本与 PostgreSQL 软件主版本分开管理。
- PostgreSQL 18 → 其他主版本的升级不是改镜像标签，须安排原生数据库迁移及本程序的兼容验证。
- 回退前先保留当前完整状态，在隔离目标用旧程序与对应旧备份验证；已经升级的数据库不能保证被旧程序直接打开。
- 按公司的要求保留多份不同时间的备份。例如每日备份、每次升级前完整包、定期异机演练；频率由可接受的数据损失时间决定。
- 删除前确认至少有已验证的异机副本，核对精确文件名和时间。待恢复标记、安全副本和原主密钥不作为普通缓存删除。

## 9. 恢复失败时怎么办

| 提示/现象 | 处理方式 |
| --- | --- |
| 密码错误/包损坏 | 核对包密码与文件摘要，重新复制备份；不反复修改包内容 |
| 需要确认文本 | .dump 恢复输入 `RESTORE DATABASE`；完整迁移创建/恢复输入 `MIGRATE` |
| 已暂存却没有变化 | 还没执行维护命令；刷新网页、普通重启、`--initialize-only` 都不能代替恢复 |
| 另一个实例占用数据库 | 先停止原 API，检查重复容器/服务/前台进程 |
| 维护连接和业务连接不一致 | 核对两个文件的主机、端口、数据库名，不修改真实库来迁就错误连接 |
| 缺 pg_dump/pg_restore | 恢复完整程序包中的 `Tools/PostgreSQL` 及依赖，不能只复制主程序 |
| 权限不足 | 按部署指南恢复 NOLOGIN owner、维护成员关系和独立业务角色 |
| 磁盘满/文件不可写 | 保留待恢复目录，处理磁盘/运行账号权限后重试同一维护命令 |
| 数据库版本不支持 | 使用兼容程序/备份，在隔离目标核实；不要删除旧库或改版本标记 |

维护开始前会创建 `before-restore.dump`。普通数据库恢复的安全目录为 `DataRoot/Backups/PostgreSQL/safety-恢复编号`；完整迁移为 `DataRoot/Backups/ServerMigration/pending-编号`，其中还可能保留旧文件和替换日志。失败时保留这些目录和 `.pending-restore.json`，修正原因后重试同一命令。

程序会尝试事务/文件回滚；如果回滚也失败，会明确停止。**不要手工删除待恢复标记让程序勉强启动。**请管理员根据安全副本和日志在隔离目标恢复，确认数据库、密钥和模板处于同一状态。

“生成还原脚本”仅供数据库管理员复核后的离线维护，它不执行恢复，也不替代本指南的实例锁、schema 校验和整体回退流程。普通用户使用界面暂存加维护命令即可。
