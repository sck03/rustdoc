## 1. 目标与明确决策

1. **只有 A 也能首次部署和正常使用。** A 运行 React/Rust 应用和 PostgreSQL 18，附件默认使用 A 的 `DataRoot/Files`（镜像部署为 `data/Files`）。不要求先购买 B、填写 S3、接移动硬盘或设置异机备份。
2. **B 是以后可选的附件扩容位置。** 保留 S3 与已登记目录两种接法；NFS 由宿主部署层挂载，应用按受管目录使用。接入 B 不迁走 PostgreSQL，也不改变业务入口。
3. **备份目标独立选择。** 可以先使用 A 的受管备份目录，也可直接写独立设备 C、S3、受管 NFS 目录或插在 A 上的移动硬盘。同在 A 的备份只提供本机回退，不宣称能抵御 A 整机故障。
4. **保留一个通用申请入口。** 申请人选中文类别和具体事项；审批人与办理人分别解析、分别展示。用印、证明、IT、维修、其他事项统一遵守显式办理规则。
5. **错误必须可定位、可处理。** OA 指出出错流程、节点、缺少的配置或资格；其它模块区分实际失败原因，给出出错位置、处理建议及必要的追踪编号。
6. **采用一次新的正式数据与接口基线，不维护旧软件兼容链。** 本批源码采用全新 schema 19，替代起点 schema 18。新数据库、新 API、备份格式与前后端同步交付；不编写旧库迁移、双写、旧字段别名或旧包转换器。
7. 保持模块化单体、单业务 API 实例、既有任务系统、同一 React 前端、Tauri 宿主边界。不引入 Redis、消息队列、第二业务库、LocalStorage 或替代 UI 框架。

不兼容旧软件不等于删除历史业务语义：新系统内已发布流程、已签意见、历次提交、文件版本、审批 PDF、审计和有效恢复点仍须保留。开发与演练只用显式新 DataRoot/数据库；本方案不授权清空现有数据或备份。

## 3. 模块边界与复用方式

```text
React 页面 / Tauri 宿主 / 独立维护页面
                  ↓ 同一 native_contract 生成的类型与访问元数据
Rust HTTP 适配器 / 独立维护宿主
                  ↓
Engine：申请编排、办理选择、备份任务、恢复状态机、清理执行
       ↓ 纯规则                    ↓ 显式端口
Domain：类别/流程/保留规则       Storage：SQL/事务/分页/两库适配
                                  文件与网络适配：受管目录/S3/WebDAV
```

| 位置 | 改造职责 | 边界 |
| --- | --- | --- |
| `export-doc-domain/src/oa` | 类别适用规则、办理要求、条件检查、不可变提交语义 | 不读数据库、不取路径、不判断 HTTP 状态 |
| `export-doc-engine/src/engine/oa` 与 `handling` | 统一选择/解析、发布覆盖、当前资格、在途交接 | 延用现有审批内核；只拆出职责明确的模块，不继续扩大 `oa/mod.rs` |
| `export-doc-storage` | 办理目录、引用保护、恢复点索引、保留策略、分页和事务 | SQL 只在这里；SQLite/PostgreSQL 同一业务契约 |
| `engine/file_store` | 生产文件库、位置身份、流式读取/写入、迁移、完整性与回收 | `FileStore` 继续是唯一生产文件访问入口；新增流式校验不能降低原件下载校验标准 |
| `engine/team_backup` | `repository`、`capture`、`restore`、`retention` 等内部模块 | 计划、立即备份、便携导出、迁移和恢复复用一套格式及用例 |
| `export-doc-network`、现有受控进程/路径模块 | S3/WebDAV 传输、pg_dump/pg_restore、挂载/介质身份适配 | 不复制 SigV4、进程树取消、磁盘预算或平台路径校验 |
| `apps/export-doc-server` | 业务模式与独立维护模式的组合根、HTTP 生命周期 | 业务模式无 DDL 凭据；维护不依赖可用业务数据库，不使用 Docker socket |
| `apps/export-doc-web/src/features/oa`、`features/settings` | 页面组合、独立草稿/查询/命令 hook、错误呈现 | 不在组件中判断派单规则、猜测后端失败原因或拼服务器路径 |
| `export-doc-contracts::native_contract` | 类别 ID/标签目录、DTO、端点、错误码、权限、超时/响应容量 | 统一生成 OpenAPI/客户端；不手改生成文件或另写维护 API schema |

先在现有 crate 内按责任拆模块。只有独立部署或 feature 裁剪确有收益时才增 crate；不能为了目录整齐引入依赖环、转发层或重复实现。桌面不带 PostgreSQL 服务端适配器，网页不带 Tauri。

当前 Cargo 依赖方向是 Domain → Contracts，保持这一方向。共享类别 ID/标签及错误形状放在原生契约目录，Domain 消费生成类型并实现纯业务政策；Engine 将政策和当前发布配置组合为可选目录。Contracts 不反向引用 Domain，前端不得另写第二份类别枚举。

扩展点保持少而明确：`DatabaseSnapshotProvider` 负责同快照捕获/校验/恢复；`BackupRepository` 负责流式对象、能力探测、条件提交、读取和受控删除；`LocationProbe` 负责已登记目录与介质身份；办理责任解析复用现有来源接口；错误描述由各领域类型投影到统一响应。各接口显式携带取消/期限/预算，不用任意 JSON 或函数名字符串组成插件框架。新厂商接入只增加对应适配器及契约测试；新 OA 类别只扩展目录/规则及专业字段，不复制整套页面。PITR、STS 自动刷新、多实例和宿主自动挂载需要独立需求与验收，不为未来假设提前建设服务。

## 4. 全项目可解释错误契约（优先基础批次）

### 4.1 返回什么

扩展唯一 `ApiErrorResponse`，统一用于 HTTP、后台任务终态、预检问题列表和维护接口。建议字段如下；字段名在实施时从原生定义生成，下面不是第二套正式契约。

| 字段 | 含义 |
| --- | --- |
| `code`、`message` | 必填稳定错误码与可直接显示的中文原因；禁止只按状态码生成“操作失败” |
| `issues[]` | 多个独立缺项，每项含 code、字段路径、原因、处理建议；有数量上限，超限分页/给出总数 |
| `context` | 经权限裁剪的流程/节点/单位/事项/文件/目标名称；不得泄露无权查看的对象 |
| `actions[]` | 类型化动作，例如修改字段、打开有权访问的设置、刷新、查询回执、重试读取、联系管理员；不返回任意执行脚本或任意跳转 URL |
| `retryability`、`outcome` | 是否可重试；明确未执行、已提交、结果待确认。结果不明时先查 commandKey 回执，不能引导盲目重发写入 |
| `requestId`、可选 `jobId` | 请求/任务追踪；用于复制错误详情和管理员诊断 |

Domain 返回类型化原因；Storage/网络/文件/工具适配器保留受控原因类别；Engine 补业务上下文和授权后的动作；HTTP 统一映射状态和安全输出。原始驱动/系统异常仅进入脱敏诊断，不能拼入公共 message。删除前端按中文 message/正则猜错误码的分支。

保留现有分类：校验 400、登录失效 401、权限 403、明确不存在 404、版本/状态冲突 409、忙碌/准入 429、内部缺陷 500、未提供能力 501、依赖故障 503、期限到达 504；取消沿用现行取消边界。权限错误不得伪装成缺配置；I/O 故障不得改成 404/409 或空列表。

### 4.2 OA 必须指出的具体原因

| 原因码示意 | 普通用户应看到的内容 | 管理员定位 |
| --- | --- | --- |
| `OA_HANDLING_SERVICE_REQUIRED` | “维修申请尚未选择办理事项，请选择后提交。” | 定位申请的“办理事项”字段 |
| `OA_HANDLING_SERVICE_UNCONFIGURED` | “维修类别尚未配置可用办理事项，请联系流程管理员。” | 定位当前单位的办理分工及维修类别 |
| `OA_APPOINTMENT_MISSING` | “申请人没有当前单位的有效任职，无法确定部门审批人。” | 组织与任职，显示缺失/未到生效日/已到期的具体原因 |
| `OA_APPROVER_SOURCE_EMPTY` | “部门审批节点无法找到业务部的有效负责人。” | 定位发布版本、节点、部门与负责人来源 |
| `OA_HANDLER_ACCOUNT_DISABLED` | “账号权限办理事项的指定办理人账号已停用。” | 在有人员查看权限时显示具体人员；同时列出未生效任职或未关联账号等不同缺项 |
| `OA_HANDLER_PERMISSION_MISSING` | “指定办理人缺少‘通用申请／完成办理’权限。” | 给出缺少动作及单位/部门/项目范围；不能自动扩权 |
| `OA_INDEPENDENT_REVIEW_UNSATISFIED` | “独立复核节点与前一节点只有同一位有效责任人。” | 指出冲突的两个节点，不泛称“流程配置错误” |
| `OA_PUBLICATION_STALE` | “办理分工已修改，原发布核验已过期，请重新核验。” | 定位目录修订和受影响样例 |

依赖数据库失败时停止资格诊断并返回数据库原因，不能把读取失败算成“无人可办”。一次预检可汇总能够确定的独立缺项；未知项标记未核验，不能捏造原因。普通用户无配置权限时提供准确缺项和联系管理员提示，管理员才显示配置入口与受限详情。

### 4.3 其它模块同样执行

- 存储：区分目标未登记、介质未插入、库身份不符、网络/DNS/连接超时、S3 凭据拒绝、桶/前缀权限不足、对象缺失、摘要不符、空间不足。只在适配器确实能分辨时使用细分类；无法确定则显示已知失败阶段和追踪编号。
- 数据库：区分连接拒绝、认证失败、连接池繁忙、查询超时、schema/模型不符与事务结果不明。业务页面不显示连接串、用户名密码或 SQL。
- 导入/单证/报表/OCR：定位文件、工作表、行列/字段、模板组件或页码，说明非法值、缺字段、缺可选组件、格式不支持、容量或期限超限；保留原草稿与成功项。
- 授权/并发/下载：说明当前身份缺哪个允许公开的动作、记录版本已变化或票据过期；未经授权不能披露隐藏记录是否存在。下载已开始后无法再返回 JSON 时，任务/下载记录必须记录原因，客户端不能将截断文件提示为成功。
- 前端所有错误统一走共享模型与组件：字段下显示缺项；折叠区有错误自动展开并定位；多节点错误用可展开列表；诊断详情按需展开。正常界面不常驻长说明。
- 删除 HTTP 对多数 5xx 的一刀切替换，改为“经审核的安全 message + 脱敏诊断编号”。未知缺陷使用“在某步骤发生未分类错误，未确认是否提交，请查询处理结果”，同时保留追踪线索，不能凭空给出具体根因。

这一要求覆盖全项目。实施时先盘点错误构造点、转换器、任务终态和前端显示点，按 OA、文件/备份、业务录入/导入、报表/OCR、授权/设置分批替换；验收以失败场景证明可定位，不以错误码数量充当完成证据。

## 5. 通用申请的完整重构

### 5.1 类别、事项与办理职责

- 内置类别维持用印、证明开具、IT 支持、维修、其他事项；稳定内部标识不暴露给日常操作人员。类别 ID/标签集中在 native_contract 目录并生成两端类型，默认办理要求由 Domain 使用该类型判定，Engine 返回当前发布政策；删除多份前后端手写清单，保持现有依赖方向。
- 办理事项为单位范围内的独立实体：稳定 `serviceId`、`categoryId`、名称、启用状态、版本和办理人绑定；使用现有人员/任职/账号关系，不新建另一套人员目录。改为有界分页查询及已选 ID 回显，不让目录规模受整个设置对象数组限制。
- 用印、证明、IT、维修默认都要求办理。其他事项默认也要求办理；确属仅审批的用途，由管理员在流程发布配置中显式选“无需办理”，普通申请人不能绕过。
- 流程发布版本冻结 `handlingRequirement`；每个启用类别都必须有定义。需要办理的路线必须到达合法办理节点；不需要办理的路线不得保留依赖办理人的节点，也不得跳过用印等必需业务动作。
- 同类别恰好一个**启用且对当前申请身份适用**的事项可自动选中；多个时明确选择；零个时允许保存草稿、禁止提交。新建与换类别清空旧选择，禁止跨类别沿用；读取失败不能当作零个事项。
- 草稿回显已停用/已失效事项及原因，但不得自动替换已保存的选择；重新选择后才可提交。最终服务端始终验证显式 serviceId、目录修订及当前权限；用户界面上的自动选择不构成授权。

### 5.2 同一条解析链路

申请编辑、提交前预览、仿真、发布、正式提交统一调用“解析申请上下文 → 核验事项 → 解析审批人/办理人 → 校验图与资格”。纯规则归 Domain，目录查询归 Storage，Engine 只组合结果。删除通用申请 Handlers 在缺少事项时扫描通用候选人的分支；其它业务来源逐项核对，避免误删合法的财务/资源责任来源。

正式提交同事务冻结流程版本、类别/事项 ID 与显示名称、办理规则版本及初始责任快照，发布任务和通知。签署/办理仍复核当前账号、任职、动作权限及材料范围。停用人员不使旧通知继续有效；在途任务只能通过有原因、有版本校验的交接变更，保留原始责任和历史签署。

审批通过与完成办理分别进入现有状态机。需要办理时先 Approved，办理成功才 Completed；无需办理的路线由显式规则结束，不伪造一次“已用印/已维修”。保留财务 HandedOff 等其他业务终态及 13 类流程的专业约束。

### 5.3 发布核验与前端操作

流程编辑的条件选中文类别和具体事项；不显示“请输入类别代码”。仿真增加事项选项，结果按审批与办理两阶段列出节点、实际责任人、来源和阻断原因；更换人员、类别、事项、项目、任职或配置版本后旧结果失效。

发布使用两层检查：对所有启用事项做目录/资格完整性检查；对流程每个可达类别分支、仅审批分支、事项特定分支及关键任职/项目条件运行样例。生成覆盖报告，不把同一类别的一个成功样例视为其它事项都通过。复用现有人工样例上限；目录完整性检查采用后台分页，不把数百事项塞进发布请求。复杂条件不能证明覆盖时列出缺少的具体样例，不声称数学上的全输入证明。

仿真不创建申请、任务或通知。发布请求带预期流程版本、事项目录修订及核验摘要，服务端重新核对；定时启用再次检查，条件变化则受阻并给出明确缺项。新增/启用事项须满足当前启用流程的办理约束，不能借新增配置绕过发布检查。

申请页只保留“申请类别”“办理事项”和必要结果；一个事项自动带出，多项可搜索选择。办理分工页显示“事项／类别／办理人员／状态”，多人“任一办理”语义沿用现行规则。审批人确实因类别不同才设置审批分支，不复制多套通用申请页面。

## 6. 从单机 A 到可选 B/C 的存储路径

| 阶段 | 默认操作 | 完成条件 |
| --- | --- | --- |
| 仅 A 首次部署 | 启动应用和 PostgreSQL；创建管理员；默认本地附件 | 不要求远端配置即可录入、上传、预览、下载及打印；新库只在确认不存在时初始化 |
| 仅 A 备份 | 用户可选 A 上受管备份目录并启用计划 | 明示“备份在本机”；不开备份不阻断业务；不默认删除业务文件腾空间 |
| 后续接入 B | S3 在网页登记；NFS/独立盘先在部署面板挂载登记，然后网页核验并迁移 | 保留原文件库至目标核验和切换完成；旧附件、新上传和重启后读写通过 |
| 增加独立备份 C | 网页选目标并核验，执行首次完整恢复点 | C 有独立仓库身份及可解锁材料；同 B 另一桶不自动算独立设备 |
| 移动硬盘离线副本 | 首次登记后，插入正确介质，在网页备份或复制恢复点 | 写入、回读与同步均完成后提示可安全移除；由宿主系统弹出 |

### 6.1 文件库与备份仓库分离

生产 `FileStore` 继续提供本地/S3；备份 `BackupRepository` 提供受管目录、S3、WebDAV 三种适配。目录适配同时接受内置 `DataRoot/Backups` 专用子目录与组合根登记的外部位置；网页仍只选择目标 ID。WebDAV 保留当前用途，但改用新仓库格式及同一备份用例，不保留“先生成旧大包再上传”链路。NFS 和移动硬盘属于已登记目录的不同介质能力，不新增 NFS/USB 业务协议。

统一类型：生产 `StoreId`、备份 `RepositoryId`、部署登记 `LocationId`、可移动 `MediaId` 分别表示不同身份。配置保存 locationId + 相对子目录或 S3 endpoint/bucket/prefix，凭据仍由主密钥保护。已有生产库不得当空目录初始化；备份仓库不得与生产对象前缀、Database/Security/Templates/Cache 等其它用途根重叠；本机备份只进入上述 Backups 专用子目录。多个目标不能同时对同一仓库拥有写权限。

网页只显示可选名称、用途、连接状态和容量，日常人员不用输入宿主绝对路径。没有 B 时选默认本地文件库是正常配置；已经切到 B 后，B 掉线、身份改变、目录被卸载必须明确失败，不能自动回退 A。

### 6.2 介质与挂载核验

组合根登记受管挂载并验证现存目录、祖先链接、权限及用途。移动介质除仓库标记外，核对平台适配器可取得的卷/挂载身份；不能只凭目录名或 `.store-id` 文件判断“盘还在”。写前、重新连接、恢复/提交前复核身份；中途换盘保留未完成状态，禁止把缺失挂载下的本地空目录当目标。

Docker 的目录由 daemon 所在宿主管理，浏览器电脑的盘不会自动成为容器目录。热插拔是否可见取决于宿主挂载和容器传播配置；首版允许部署面板重新挂载/重启对应服务后再核验，不承诺所有 NAS/Windows/Linux 均能无感热插拔。写入同步成功后只提示“可在系统中安全弹出”，项目网页不虚构已物理卸载。

插在办公电脑上的硬盘通过浏览器下载便携恢复包；无法用于服务器无人值守任务。浏览器下载用流与有界缓存，不能整包读入 Blob。常规“下载完成”只能表示传输完成，不能代替移动盘上的完整性校验。

## 7. 统一加密恢复点仓库

### 7.1 以恢复点替代反复全量大包

每个恢复点包含：数据库类型/schema/模型指纹、数据库快照、完整的文件对象清单、用户模板、匹配的应用主密钥、必要应用配置、生产库身份和位置描述、创建时间/业务时区、软件构建信息及内容摘要。部署拓扑清单随恢复点保存；宿主挂载、TLS 和运维 secret 的备份由部署管理员明确导入受控加密配置区，不能自动抓取宿主任意文件或声称包内已包含所有部署凭据。

附件按内容去重，每个恢复点保存**独立完整清单**，不依赖前一恢复点的差异链。只传新对象，数据库每次先做完整逻辑快照；大规模 WAL/PITR 属独立后续能力，本批不混入。恢复点的“独立”指清单自足，不代表可以脱离其引用的仓库对象单独复制 manifest 就恢复。

实际仓库为适配目录/S3/WebDAV 的平面受管命名空间：

```text
repository.json                 仓库身份与被密码包裹的根密钥
credential-*                    不可变密码轮换记录
blob-*                          加密去重对象块
manifest-<point-id>-<page>       加密分页完整清单
point-<point-id>.commit          最后发布的认证提交记录
writer-lock / writer-session    远端写入所有权与会话保护
```

目录布局通过受管仓库适配器实现。数据库中的恢复点列表只是可重建索引，A 完全损坏时可用仓库身份、COMMIT、manifest 和离线保管的解锁材料发现恢复点，不能依赖 A 中唯一的备份目录索引。

### 7.2 数据库与附件必须属于同一时点

1. 取得现有备份/回收协调边界，持久登记捕获意图；先等待已认领的删除完成，禁止新的物理回收。普通业务写入仅在需要取得一致快照的短阶段等待。
2. PostgreSQL 在 Storage 内打开只读可重复读快照，并导出 snapshot 标识；`pg_dump --snapshot` 与文件清单分页读取使用同一快照。导出事务保持到 pg_dump 与清单读取都结束，有总期限；取消/崩溃后该快照不可重用，重新捕获新的恢复点。
3. SQLite 使用同一已完成数据库快照读取文件清单，禁止从复制后的数据库配合当前实时目录扫描拼出恢复点。只读快照文件是备份工件，不是第二业务数据库。
4. 模板和主密钥配置在已有模板/配置锁内取得版本一致的快照；外部字节对应不可变对象。manifest 记录配置修订与库身份，捕获期间配置切换必须等待或导致本次重试。
5. 释放数据库快照后，可继续在锁外传输已捕获对象；备份意图保护这些对象不被回收。首版复用现有粗粒度排他回收保护，业务正常写入继续允许；不要未经证明就新增一套高复杂度逐对象锁。
6. 对象、数据库、密钥与模板写完并核验后，最后发布 COMMIT，之后才能显示“可恢复”。数据库快照与清单不一致、对象缺失、取消或超时均不发布。

这项一致性须有并发新增/删除/改引用测试。当前源码顺序执行 dump 和目录读取不能直接当作已满足新快照协议；实施先复核现有锁与查询时点，明确补齐同快照证明。

### 7.3 直接传输与空间预算

从 B/A 读取 → 计算摘要 → 压缩（适合时）→ 分块认证加密 → 写备份目标，不在 A 聚合全量附件。现有 S3 生产下载会产生本地验证缓存，备份/恢复须新增专用有界流式访问：未通过摘要校验的目标一直留在 pending，不进入生产引用或恢复点。不能简单调用现有整对象缓存读取后宣称“没有本地占用”。

首次实现以完整文件对象为去重单元；对象过大时采用有限大小的认证段，不先实现通用块级增量、跨仓库去重或数据库差异链。复用锁文件中的压缩、加密和传输库，新增依赖另走审计。

空间预检分别计算：

- A 的应用工作盘：数据库快照/恢复工具必须的暂存、配置与模板快照、有限传输窗口、任务日志和 256 MiB 安全余量；PostgreSQL 卷另算目标库、WAL、索引及保留旧库空间。
- 目标 B：恢复对象实际占用、临时发布空间及存储余量；C：新数据库快照 + 新附件对象 + 清单 + 未完成分段预算。
- 若备份目标就在 A，同一文件系统的暂存与最终备份空间合并核算；“不用 A 暂存附件全量”不表示备份存 A 不占 A 容量。
- S3/WebDAV 无可靠剩余容量接口时显示“未知”，使用管理员设置的预算和实际写入错误，不伪造磁盘剩余量。

验收必须记录峰值内存/临时空间：当附件总量增大、窗口并发固定时，A 的工作空间不得按附件全量线性增长。数据库/模板所需空间不足仍须准确阻断，并列出哪个卷不足、估算需求与可用值；不能承诺任意小的 A 都可恢复。

### 7.4 加密、提交与中断恢复

沿用已有受审核加密原语，抽出单一分块密封模块。使用随机仓库根密钥、每对象随机数据密钥/nonce、认证头和结束记录，明文摘要放在加密 manifest 中；去重标识在仓库范围内用带密钥摘要派生，不采用由文件摘要直接派生密钥的收敛加密。恢复凭证仅包裹仓库密钥，与 A 的应用主密钥分开，避免 A 丢失后不能解锁自己的备份。

自动计划在 A 加密保存必要解锁材料，状态接口不回传。创建仓库后必须执行一次恢复凭证核验，并让管理员在 A 之外保管；改密码重新包裹密钥，不重加密全部对象。更换密钥世代时保留旧恢复点所需密钥，只有证明无引用才退役。格式、截断/篡改/nonce 管理测试通过后才能启用新仓库。

目录适配器使用同卷临时文件、同步和原子发布；S3 使用不可变对象键、受控条件写和最后 COMMIT；WebDAV 在探测通过的原子创建/替换语义上工作，不满足则报“目标缺少所需能力”。仓库写者租约/世代号与所有权隔离共同防止两个 A 写同一仓库；锁丢失后立即停止写和 GC，不能只靠应用进程内锁。

状态机：`Preparing → Capturing → Transferring → Verifying → Committed`，失败/取消终态不进入可恢复列表。远端已提交但本地索引未记录时，重启按提交摘要补索引；未提交的对象可在保留意图期限和审查后回收。复用任务幂等键、取消期限、分段 UploadId 日志与重试预算。连接测试成功、上传返回 200、存在 ETag 均不能代替内容核验。

首次入库对象须验证实际内容；后续对象可以复用已验证且不可变的记录，并安排周期全量校验。页面分别显示“最近写入核验”和“最近全库核验”，不得将抽样检查标成全量通过。

便携导出使用同一 manifest/对象编码封装为可顺序读取的新格式，不保留 ZIP64 全包落盘必需链路。从任意恢复点导出时收齐所有引用对象，因此移动硬盘上的自包含包可独立恢复。首版不承诺浏览器断点续传；大规模定时备份优先仓库直写。

## 8. 恢复与独立维护宿主

### 8.1 两条清晰的恢复路径

**路径一：A 更换，原文件库 B 完好。** 在新 A 独立维护页面选恢复点、解锁并核验数据库与主密钥；选择“接回原文件库”，连接原 S3/已登记目录。核对 storeId、位置身份及该恢复点引用的每个对象长度/摘要，通过后再发布数据库与配置。凭据可重新签发，不要求复用旧 S3 密码。保留 B 上不属于该恢复点的对象，不自动删除或重写 B；缺件时显示清单并转“从备份补齐/重建”流程。

**路径二：B 丢失/损坏，或原来只用 A 且 A 丢失。** 从 C/移动盘选择恢复点和一个新的目标文件库，流式解密并写到新 S3 前缀或空受管目录。也可选新 A 的本地 Files，但必须有相应容量。逐对象校验完成后恢复并核对数据库引用，最后切换运行配置。全程不在 A 解出全量附件，不覆盖身份不符的已有库。

### 8.2 维护网页不能依赖被恢复的业务库

首版采用同一 Rust 服务程序的**按需独立维护模式**和同一 React 构建中的维护入口；Compose 提供受限 `maintenance` profile，在恢复时由部署管理员通过 Docker/NAS 管理面板启动。当前一次性 `restore --restore-pending` 将与网页维护模式共用恢复用例，不能保留两套恢复器。

部署管理员在面板停止 application，启动维护服务并查看链接；之后解锁、选目标、预检、恢复与查看进度都在维护网页完成，结束后在面板恢复业务服务。无管理面板的宿主保留受控命令入口。项目网页不获得 Docker 管理、宿主挂载或任意进程执行权限；本批不承诺从普通业务网页自动启停 Docker。维护服务平时不需要常驻，也不是单 A 部署的必需运行项。

维护认证使用部署端一次性凭证和短期 HttpOnly 会话，不依赖旧管理员或可用数据库；仅绑定明确管理地址，远程访问使用已有 TLS/可信网络边界。会话、Origin/CSRF、失败限流和端点 metadata 一并定义，不按 `/maintenance` 路径猜授权。日志不保存密码、主密钥或完整恢复令牌。

维护容器只取得必要 DataRoot、登记存储位置、PostgreSQL 维护凭据及访问 B/C 的受控网络。当前 restore 仅处于内部 database 网络，新增网络接入须在 Compose 中显式配置并单独验收；业务容器仍无维护凭据，任何容器不需要 Docker socket 或 privileged。

### 8.3 可恢复的状态机与切换顺序

`Draft → Preflight → Ready → ApplyingFiles → ApplyingDatabase → Verifying → Committing → Completed`。维护日志保存在 `RuntimePaths` 注入的 `DataRoot/Recovery`，使用现有私有目录、原子日志与校验机制，不新增 SQLite 维护数据库。

- Preflight 固定恢复点、源/目标库身份、目标登记修订、数据库指纹、密钥可用性、空间与连通性，生成有限期 planId。用户确认显示会替换的目标，执行前再次核对。
- 执行须拿到应用实例/维护排他锁；业务 API 已关闭连接与后台写任务且数据库无未受控写者后才可继续。启动程序遇到 pending 标记只能提示维护，不能抢先接入半恢复库。
- 新文件库先完整准备，旧库/旧文件配置保留。数据库写入显式的新空库或当前恢复器支持的隔离目标；只在同一 PostgreSQL 服务内作受控恢复准备，不建立另一套长期业务库。
- 数据库、文件库、主密钥与配置无法跨系统做单个 ACID 事务，使用持久日志记录各步与激活代次。核验通过后发布小型激活记录；崩溃后按记录恢复/回退，不能猜“文件在就算完成”。切换账号角色/连接目标由维护适配器完成。
- 提交前可取消并清理本次未发布工件；进入切换后界面显示“正在完成切换”，等待有界收尾。结果不明保留现场与禁止启动状态，提供具体失败阶段和继续操作入口。
- 成功后撤销旧会话，使用恢复后的账号重新登录；核对新上传、旧附件、模板/PDF、审批状态与权限。安全副本保留至验收后显式清理。

恢复演练不连接真实业务目录。故障前 A 的旧实例必须隔离；不同 DataRoot 下两个 A 的本地实例锁不能防止同时操作同一个 B/C。重接已有文件库必须完成部署层断开旧 A 及仓库写者所有权确认，不能声称有集群自动防双主。

## 9. 容量、保留、归档与清理

### 9.1 四类状态分别展示

| 数据 | 默认政策 | 执行边界 |
| --- | --- | --- |
| 临时预览、可再生成导出、失败上传残留 | 沿用任务 TTL/容量预算，排除活动任务 | 自动清理本模块拥有的临时输出，失败具体说明 |
| 无引用生产对象 | 先扫描与预览，复核业务/历史引用、活动上传、捕获意图和迁移 | 标记后延迟物理回收；同摘要并发引用通过原协调机制处理 |
| 正式单证、签字原件、回执、人事和审批依据 | 默认长期保留，不按上传年龄自动删除 | 按业务档案类别，从结案/归档日期起算；暂停保留覆盖清理 |
| 备份恢复点与仓库对象 | 按显式份数/天数，至少保留策略要求的成功恢复点 | 先退役恢复点，再按全部有效 manifest 计算可回收对象；不按对象 mtime 删除 |

低频资料可按档案策略迁到已登记归档位置，沿用 `file_locations`、对象摘要与迁移任务，读取通过同一 FileStore 定位；不要复制一套“历史附件库”实现。归档只是位置变化，权限和业务引用不改变；归档服务需要取回等待时必须明确状态。

正式资料到期先进入待处理清单，显示档案类别、依据日期、引用与暂停保留原因，经有权限人员批准后再移除允许删除的业务引用并留下审计。批准删除活跃资料不等于立即从所有历史备份抹除；恢复点保留期单独执行，界面明确受哪些恢复点保护。

只有自包含且已核验的恢复点可以解除对生产库的备份捕获保护。本批不提供仅保存数据库/清单、却依赖 B 永久不清理的“完整灾备”。如果将来单独引入仅元数据恢复点，必须有独立标识、生产对象保留承诺及生命周期协议。

### 9.2 清理执行协议

预览返回候选、原因、预计释放量、受保护量、目录/策略版本及短期 token；执行按 token 复核当前权限、引用与版本。任何新引用、活动恢复、目录变更或无法读取 manifest 都使相关范围停止清理。离线移动盘显示“待连接后执行”，不能当作空仓库回收索引。

仓库回收采用标记→隔离/待删除→重新核验→删除→审计；活跃读、备份、导出、恢复及密钥世代都有保护。远端中断后可重试，删除失败保留可追踪条目，不静默报成功。生产对象和备份对象的锁、状态与保留期分别维护，但共用摘要、路径和任务基础模块。

### 9.3 容量看板与告警

显示 A 数据库/运行盘、生产文件库、备份目标三个区域；分开呈现逻辑引用量、物理去重占用、近期新增、可回收量、受保护量、最后核验时间和最近成功恢复点。S3 未知总容量显示未知，不能用对象合计反推总空间。

Storage 维护按用途/单位汇总和有界日汇总，页面不扫描全库；现有文件总量触发器继续复用。告警接入现有通知系统，按“正常→接近阈值→超过阈值→恢复”去重，详细原因指向具体卷/仓库。用户可配置容量阈值与增长观察期，告警不能自动触发正式资料删除。

## 10. 新数据与接口基线

### 10.1 数据落点

以下保留设计时的数据模型；实际表/索引以 Storage DDL 和新基线数据字典为准。完整 DDL、外键、索引、两库指纹在基础批次进入 Storage，并同步数据字典。先实现新基线，再运行新测试数据；不在现有 schema 18 数据库上自动升级。

| 模型/建议表 | 关键数据与约束 |
| --- | --- |
| `handling_services` | 稳定 ID、单位 ID、业务种类、类别 ID、名称、启用状态、revision；索引单位/种类/类别/状态/ID；有历史引用时停用，不直接删除或改类别 |
| `handling_service_assignees` | serviceId、personId、有效任职 ID、有效期；复用现有人事身份及账号解析；唯一约束防重复绑定，不独立保存第二份人员资料 |
| 发布定义/申请提交快照 | 扩展现有模型的 handlingRequirement、serviceId/serviceRevision、名称与责任快照；仍使用原流程任务/提交/签署模型 |
| 恢复点与运行索引 | repositoryId、pointId、manifestDigest、状态、统计、核验时间、jobId/幂等键；唯一 repositoryId+pointId；可从仓库提交记录重建 |
| `retention_policies`、`retention_holds` | 业务档案类型、起算事件、期限、批准规则、暂停原因/解除记录、revision；不按文件后缀决定业务保留 |
| 清理计划/明细 | 预检 token、策略/目录版本、分页候选、引用核验结果、到期时间、执行状态；复用任务系统，不增加队列服务 |
| 容量日汇总 | 日期、用途/位置、物理/逻辑占用、新增/回收；沿用现有实时汇总校验，不持久化前端计算值 |

仓库身份、启动所需登记信息、加密凭据及恢复日志位于 RuntimePaths 下的受管私有配置，故障时无需先读业务库。数据库只维护业务策略及查询索引；同一配置字段明确一个权威来源，不制造 SQL 与 JSON 两份可独立修改的真值。备份端 COMMIT/manifest 是恢复点真实性依据。

建议新仓库 magic 为 `EDM-BACKUP-REPOSITORY-1`，便携封装为 `EDM-RECOVERY-BUNDLE-1`，实现时固定在唯一格式模块。它们是新协议，不是现行密封 v2 的兼容分支。旧包仍留在原位置；新程序识别不支持格式后说明需要原版本工具处理，不自动转换或删除。

### 10.2 API 用例清单

路径为实施建议，不是已存在的接口。沿用 `/openapi/v1.json` 为唯一对外契约；维护宿主只装载同一原生定义中标记为维护用途的端点。现有可复用端点按新字段直接修订，不同时保留旧别名；generated 文件只能由生成器更新。

| 用例与建议路径 | 必要输入/输出 | 权限与发布边界 |
| --- | --- | --- |
| `GET /api/oa/general/catalog` | 中文类别、已发布办理要求、目录修订 | 当前单位/任职可见范围，不泄露其它单位分工 |
| `GET /api/oa/handling-services` | 类别/用途/搜索、游标、已选 ID；分页事项及选择资格 | 管理目录与申请选项复用查询规则，按动作裁剪字段 |
| 事项创建/修改/停用 | serviceId、assignees、expectedVersion | 流程管理权限，引用/在途交接核验 |
| 申请保存/预览/提交（修订原接口） | categoryId、serviceId、版本、commandKey；分类错误 | 申请权限；提交重新解析，不信任前端自动带出 |
| 仿真/核验/发布（修订原接口） | 完整申请上下文、样例、目录修订、coverageToken | 管理权限；仿真无副作用，发布重新核对 |
| `GET /api/storage/locations` | 登记位置、能力、身份/介质状态 | 存储管理权限；不提供任意路径浏览 |
| 目标核验/迁移（修订原接口） | targetId、配置修订、probeToken；任务 ID | 探测只写本次私有探针，清理失败可见；切换带版本 |
| `/api/backup/repositories`、`/api/backup/plans` | 目标注册、加密配置、时间/保留策略 | 备份管理权限，secret 只写不读 |
| `/api/backup/points` | 分页列表、运行/核验/导出任务、退役预检 | 所有权和仓库身份复核；不存在半成品成功态 |
| `/api/maintenance/recovery-plans`、`/api/maintenance/recovery-runs` | 来源、模式、目标、planId、确认/幂等键；进度/原因 | 独立维护会话；预检和执行分离，DDL 不经普通 API |
| `/api/storage/usage`、`/api/storage/retention-policies` | 汇总、政策及暂停保留 | 统计与策略分别授权；无法取值显示未知 |
| `/api/storage/cleanup-previews`、`/api/storage/cleanup-runs` | 范围、策略、预检 token、确认；任务 ID | 执行时重新授权/查引用，不凭过期候选删除 |

长操作返回既有任务 ID，查询分页、有总期限并支持取消；HTTP 等待不占全程数据库连接。原生成器须同步验证认证、许可要求、动作范围、请求/响应容量和全部错误状态。错误码枚举按领域维护、统一汇总，不使用自由字符串约定替代正式 schema。

退役清单与新调用点一起提交：`handlingKey`/类别代码输入旧模型、缺事项的通用候选回退、旧备份整包中间链路、固定本地 Files 的唯一恢复路径、含义错误的 `PhysicalBackup` API/任务命名及对多数 5xx 的统一模糊替换。删除前逐一核对生产引用、生成契约与真实回归；不能仅按文本相似度删除共用实现。

桌面按现有 edition/feature 显示有权使用的能力，Full SQLite 测试不代表 Document/Sales 获得全部 OA。服务端 UI 根据 endpoint/capability metadata 展示维护和远端能力；不从网址猜产品版本。

### 11.2 必须沿用的交互规范

- 所有字体、字号、颜色、圆角、间距、焦点与状态取 `styles/tokens/`；使用现有 Dialog、表单、分页、InlineNotice、CollapsibleSection、工作区容器。全局响应断点只用 680/1180，控件宽度靠布局适配。
- 常用字段及相关操作同排；窄屏统一换行。保留字段标签和必要单位，不把说明放成装饰性副标题，不用占位符替代标签。
- 常用区默认展开；高级网络、保留策略、原始诊断等默认收起。折叠状态只在本页会话保存，收起不丢草稿/校验；出错自动展开并将焦点移到明确错误。
- 操作页面没有无关的全局“保存全部”；计划、目录和政策分别有版本化保存。页面组合、草稿、查询/变更、轮询、错误模型分模块；复用现有取消/草稿保护/回执确认。
- 目录搜索防抖、取消过时查询，已选项独立回显；更换账号/单位/任职时取消旧请求及待确认操作，旧结果不能回填。
- 任务刷新沿用共享可见性和退避策略，终态停止；流式下载不把大文件放 Mutation 缓存、React state 或 LocalStorage。
- 中文 IME composition 期间 Enter 不触发提交；键盘可到达全部字段、错误项与操作；自动选事项要让屏幕阅读器感知，但不增加重复提示。
- 恢复/删除确认展示具体恢复点、目标和影响；先预检得到真实可执行计划再确认，不要求用户批准空泛操作。

| M01 | 移动盘拔出、换盘、满盘、重新挂载、系统同步失败 | 不落回 A；不标成功；同盘续作/新任务规则明确；只有核验同步完成才提示安全移除 |

## 15. 外部协议依据

2026-11-27 读取下列官方文档核对协议边界，均为设计依据，不是本项目真机验证。具体厂商兼容性由 P3/P8 证据决定。

- PostgreSQL 18 `pg_dump`：同步快照参数 `--snapshot`，用于数据库与文件清单同一读取时点。来源：`https://www.postgresql.org/docs/18/app-pgdump.html`。
- Docker Engine Bind mounts：挂载来源属于 daemon 宿主，不能把浏览器电脑的目录当作容器宿主目录。来源：`https://docs.docker.com/engine/storage/bind-mounts/`。
- Amazon S3 Checking object integrity：分段/加密场景下 ETag 不能统一当作内容摘要，使用协议校验和与本应用摘要核验。来源：`https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html`。
