# 程序整体重构与优化方案（二期，目标态）

> 编制日期：2026-11-03。状态：**方案，未实施**。依据：对 `main`（`cdb46d16`）工作树的源码核对、四份只读深审报告（存储、引擎、服务端与桌面宿主、测试与文档）以及本人对契约层与前端产物的直接测量。每条问题都标注"已复核"（本人逐行核对）或"代理报告"（审查代理给出证据、本人抽核同类项后采信）。
>
> 用户授权与边界（2026-11-03 重申）：尚未部署生产，**数据库与接口可以重新设计，不保留旧库与旧接口兼容**；OA 审批、公司组织、人员、账号与权限、模块显隐及其它模块都在范围内；**业务（客户/供货商/商品）与单证数据保持独立，不联通**；**单证继续靠 Excel 导入与手工录入**。本文沿用[OA 审批与组织权限整体重构执行方案](./OA审批与组织权限整体重构执行方案.md)的一期成果与边界；前端表现层由[前端界面重构执行方案](./前端界面重构执行方案.md)、[前端设计系统规范](./前端设计系统规范.md)、[前端信息架构与页面分配方案](./前端信息架构与页面分配方案.md)承担，本文只定义顺序与接口。

## 0. 结论

**需要一次有边界的二期重构，不需要第三次推倒重来。** 一期（schema 12、OA 内核、权限模型）经 83 组 Rust 测试、真实 PostgreSQL 18 合同与容量测试、三版桌面回归验证，保留。二期把精力放在五处已被证据坐实的"包袱"与缺陷上：

1. **契约层脱掉 .NET 包袱。** 当前 753 个操作是用 36 个 Rust 模块、5,311 行 JSON 补丁，在一份 60,958 行的冻结 .NET OpenAPI 基线上逐路径改写拼出来的；发布契约 128,934 行、运行时契约 124,543 行、生成的 Rust DTO 23,037 行。改为 Rust 原生的单一契约定义，一次性重生成两端客户端，React 客户端按域拆分（现在 754 个方法全部打进入口 chunk）。
2. **存储层做 schema 13 一次性新基线。** 核心问题：所有列表查询经 `record_rows` 视图读取，视图用表达式重组 `body`，使 `records` 上 13 个 JSON 表达式索引全部不可达；搜索无 FTS，逐行 `instr`；审计双写；若干死对象。延续"全新建库、拒绝旧库"的策略，不做迁移链。
3. **引擎层修五个已核实的稳定性/性能缺陷**（任务重试可重复执行、每个需许可操作做 ECDSA 验签并串在全局锁上、流程调度线程无健康检查、AI 子进程无并发门、登录限流竞态），并收敛重复 helper、删除死 API。
4. **宿主层修关闭竞态、主线程阻塞与更新器退出路径**，删死命令与重复的包清单。
5. **测试、脚本与 CI 收敛**：14 个测试脚本未接入任何门禁（含唯一覆盖高级流程 UI 的脚本），4 个死脚本共约 14,000 行，夹具与 harness 多套并行，三个桌面工作流只差三行。

前端按既有三份文档执行，并入本文排期（§9）。

明确不做：不改业务边界（销售域与单证域独立、Excel/手工制单）；不引入新运行依赖、UI 库、Redis、消息队列、第二业务库或微服务；不迁移旧库、旧备份；不放宽任何既有门禁阈值；不做 Authenticode/公证。

### 1.2 已核实的运行时事实

- `contracts::contract()` 以 `OnceLock` 缓存一次解析（`contracts.rs:5-10`），服务端每请求读契约不重复解析。
- 路由由 `ALL_OPERATIONS` 循环注册，无手写路由表；请求/响应校验、策略、超时都从契约读取。
- 许可检查 `licensing::check_operation`（`licensing.rs:697-724`）对每个 `requiresLicense` 操作：取 `license_gate` 全局互斥锁 → `ensure_anchor` 读库并解密 → 计算机器身份 → `verifier.validate` 做 ECDSA。
- `record_rows` 视图（`workflow_runtime_sqlite.sql:164-172`）用 `json_group_object/json_set` 重组 `body`，并左联 `request_revisions`、`workflow_instances`、`workflow_plans`、`handling_tasks`；分页与计数均 `FROM record_rows r`（`sqlite.rs:412,443`）。
- 审计写入同时插入 `history`（`body` 恒 `'{}'`）与 `audit_logs`（`sqlite.rs:513-516`）。
- 两库搜索规范化不同源：PostgreSQL `exportdoc_record_text` 按键排序 `COLLATE "C"`（`postgres.sql:121-128`），SQLite 用 serde `preserve_order` + NFC + 小写（`sqlite/search.rs:12-22`）。
- 审计查询一次 `json_group_array` 最多 200,000 行（`sqlite.rs:254`）。
- 桌面 `stop()` 无论是否真正拿到 host 都调用 `complete()`（`desktop_runtime.rs:106-121`）。
- `schedule_data_root_migration` 是同步 `#[tauri::command]`（`desktop_commands.rs:48-72`）。
- 更新器插件在 Windows 上 `on_before_exit` 后 `std::process::exit(0)`（vendored `tauri-plugin-updater-2.14.0/src/updater.rs:403,1017`）。
- Tauri 命令 `select_receipt_file(s)` 在 `desktopBridge.ts` 中零引用。
- `test_oa_advanced_ui`、`test_permission_navigation_ui`、`test_native_desktop_editions`、`smoke-web-runtime-diagnostics` 在 `package.json`、工作流、`.ps1/.cmd` 中零引用。

## 4. 设计原则（二期）

1. 一事一源：契约、DDL、分页规则、搜索规范化、资源布局各只有一个定义点。
2. 新基线不兼容：schema 13 与新契约与 schema 12 同策略，全新建库/重生成客户端，拒绝旧库与旧契约组合；不写迁移链。
3. 查询先取 id 再投影：所有列表在基表上过滤排序，视图只负责投影。
4. 修复优先于重写：引擎与宿主只改有证据的缺陷与重复，不重排模块。
5. 每项改动带断言：性能项附 `EXPLAIN` 或计时证据，稳定性项附并发/故障回归，死代码删除附引用核对。
6. 业务边界不动：销售域与单证域不联通，Excel/手工制单路径逐项回归。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原生契约重定义引入隐性差异 | 两端客户端行为漂移 | 生成物逐字节对照现契约；差异白名单只含退役/去重；真实 HTTP 回归 |
| schema 13 查询路径改造回归权限过滤 | 越权或漏数据 | 范围 SQL 先于计数/分页的合同保留；8 角色真实导航/直接地址脚本 |
| FTS 语义与现搜索不同 | 用户找不到记录 | 两库同一契约测试 + 旧用例全部迁移为断言 |
| 许可缓存失效遗漏 | 注册后仍拒绝/过期仍放行 | 注册、恢复、锚点变化、业务日切换四个失效点测试 |
| 删除"只写"表丢失审计意图 | 取证能力下降 | `workflow_operations` 先补读者再决定 |
| 前端导入路径随客户端拆分变动 | 页面迁移返工 | 前端 P3 排在 RR-06 之后 |
| 脚本接线暴露长期未跑脚本的失败 | 门禁变红 | P5 先修脚本再接线，失败如实记录 |
