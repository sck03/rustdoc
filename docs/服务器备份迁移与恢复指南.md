# 备份、整机迁移与恢复指南

核对日期：2026-11-28。适用全新 schema 19。旧 schema、旧 `.edmrecovery`/`.edmmigration`/ZIP 完整包明确拒绝，不自动转换、删除或覆盖。实现见[实施记录](./archive/2026-11/2026-11-27通用申请与存储灾备重构.md)，本轮入口、CI 和必要专项见[复核记录](./archive/2026-11/2026-11-28重构复核与CI修复清理.md)。

## 1. 先部署 A，再按需接入 B/C

只有 A 即可运行 React/Rust、PostgreSQL 18 和默认 DataRoot/Files。B 是可选附件设备，C 是可选独立备份位置；两者均不是登录、审批或上传的前置条件。切到登记外部文件库后，设备断开会明确报错，不把新附件写回 A。

目录和移动介质先由部署管理员挂载，再通过 `--file-store-root` 或 `EXPORTDOCMANAGER_FILE_STORE_ROOTS` 登记。目录必须已经存在，位于应用/数据目录之外且彼此不重叠。业务文件库、归档位置和恢复仓库不能互相包含。配置只保存位置编号及相对子目录，每次操作核对库标记与卷/介质身份；网页不能挂载宿主磁盘或指定任意绝对路径。

## 2. 日常灾备与便携文件

日常备份默认关闭。“备份计划”设置时间、保留份数/天数和恢复凭证；“备份位置”选择本机专用备份目录、登记目录、WebDAV 或 S3；“恢复点”查看结果、下载或用于恢复。本机目录是同机恢复材料，不能代替异机灾备。目录目标为 `recovery-<仓库编号>` 子目录，实际仓库编号应与凭证分开离线保管。

首次传输全部对象；以后复用同仓库已有加密块，每个恢复点仍保存独立完整清单和新的数据库快照，不依赖前一恢复点。全部对象、清单、数据库和匹配主密钥核验后最后发布认证提交记录，才显示可恢复。连接测试或上传成功不能代表完整恢复验证。

恢复点包含数据库快照、全部引用/保留文件、用户模板、应用主密钥及必要文件库配置。TLS、域名、宿主挂载和部署运维 secret 不会从宿主任意位置自动收集，需由部署管理员独立备份。使用环境主密钥的部署在缺少独立密钥灾备前不允许宣称可独立恢复。

“导出”生成 `.edmpoint` 自包含文件，收齐该恢复点的全部对象。浏览器采用流式下载；浏览器连接的移动盘仅能作为显式下载目的地，无人值守任务必须使用服务器已登记位置。下载结束不等于移动盘已校验或可拔出，先进行完整核验，再由操作系统安全移除。

普通 SQLite/pg_dump 数据库快照继续用于同部署维护，文件快照必须连同 `.objects.jsonl` 和邻接 Objects 目录保存。PostgreSQL 界面所称“物理备份”实际是 pg_dump custom-format；不能只复制 dump 就声称包含附件、主密钥和模板。

## 3. 空间、网络与仓库保护

附件从 A/B 直接经固定窗口流向目标；恢复时直接进入新文件库，A 不预先解包所有附件。A 仍须容纳数据库快照、恢复工具/模板所需暂存和 256 MiB 安全余量。PostgreSQL 服务器卷的空间无法从独立应用容器可靠探测，预检明确显示未知，管理员须另核目标库、WAL、索引及旧库保留空间。

S3/WebDAV 需要可靠条件创建、分页列举和回读校验，不具备这些能力的服务不接受为仓库。没有可靠总容量接口时显示未知。S3 分段传输有长度/摘要核验、取消中止和持久日志；服务器创建 UploadId 而客户端尚未取得编号的中断窗口仍须配合存储端未完成分段生命周期策略。

仓库根密钥与应用主密钥分离，密码轮换重新包裹仓库密钥，不重写所有附件。写者所有权与每次写入会话分别保护。更换 A 前必须停止并隔离旧 A；“解除中断保护”仅用于确认旧写者全部停止后的人工接管，不提供自动多主选举。

## 4. 独立维护网页

维护服务不构造业务服务，不依赖业务库登录；即使原业务库损坏或目标为空库，仍可使用部署端凭据进入维护。业务 API 和维护服务不能同时写入。

镜像 Compose 部署在原部署目录操作：

```sh
docker compose stop application
docker compose --profile maintenance up -d maintenance
# 在受控浏览器访问 http://127.0.0.1:5189/#/maintenance
# 完成恢复后：
docker compose stop maintenance
docker compose up -d --no-deps --wait application
```

默认只绑定回环地址。远程访问通过受控隧道或已有安全反向代理，不开放到不受信任网络。镜像入口生成 `config/maintenance/maintenance-token.txt`；源码入口使用原 `NATIVE_RUNTIME_ROOT` 下的同名文件。维护容器只挂必要数据和维护 secret，不挂 Docker socket、不使用 privileged；使用外部位置时按原部署登记并挂载同一编号。

1. 使用部署端凭据进入维护。会话闲置 1 小时过期，活动会话最多 8 小时；写操作仍校验同源和 CSRF。
2. 明确确认旧实例已停止并隔离。选择目录、S3、WebDAV 仓库，填写仓库编号及密码；也可把 `.edmpoint` 放入 DataRoot/Recovery/Inbox 后填写文件名，此时编号可留空并从文件读取。
3. 选择恢复点与方式：接回完好的原文件库、重建到 A、重建到登记目录、重建到新 S3 文件库。重接使用原位置编号及身份，不能创建空库冒充原 B。
4. 完整预检核对摘要、密钥、数据库 schema/模型、目标身份及可观测空间，生成 15 分钟计划。执行前再次核对目标与数据库指纹。
5. 准备文件期间可以取消；进入数据库和配置切换后等待有界收尾。切换标记存在时业务启动保持禁止。重启维护并重新解锁/预检同一恢复点后可继续既有切换，不允许新计划接管不同的待恢复点。
6. 完成后停止维护，再启动业务，使用恢复后的账号登录。

离线命令入口继续支持 `--restore-migration`，以及 `--import-migration <受管路径.edmpoint> --package-password-file <私有密码文件>`。桌面 SQLite 便携恢复仍使用现有明确选文件、校验、退出重启和恢复日志；不能把 SQLite 快照直接恢复到 PostgreSQL。

## 5. 失败、残留与空间清理

维护状态和目标意图保存于 DataRoot/Recovery。未进入切换的失败可以重新预检；“未发布的恢复工件”列出精确位置，管理员确认后可清理本次建立的独立目标，再重新恢复。S3 工件清理需要重新提供同目标凭据。

清理会核验位置、介质、库标记、目标未启用及没有等待切换任务，只删除恢复器拥有的对象。接回的原文件库、已经启用的库、完整备份仓库和恢复安全副本不进入这项清理。失败或取消保留记录以便再次处理，不把未执行的删除报告成功。

正式业务文件与恢复点分别保留。生产资料默认长期保留，到期后由另一名管理员复核处置；恢复仓库先退役恢复点，再对全部有效完整清单重算对象引用，经过 24 小时隔离及短期预检后回收。离线介质不能作为空库扫描。详见[文件存储与容量](./文件存储与容量管理.md)。

## 6. 恢复验收及能力边界

先在隔离目录/数据库演练，核对恢复后的账号权限、OA 冻结计划、旧附件、新上传、模板和实际 PDF，再切换域名或停止保留旧数据。安全副本只在核验完成后另行显式清理。

本批验证覆盖当前 Windows 宿主的必要 Rust/React/HTTP 专项及隔离 PostgreSQL 18。协议夹具不等于已验收所有 S3/NAS/WebDAV 产品；Docker 实机、NFS/移动盘拔插、Linux/macOS/ARM64、Firefox/WebKit 和生产大规模峰值测量分别记录，不能借用本机结果宣称通过。多实例高可用、PITR、STS 自动刷新、浏览器断点续传和冷存储解冻不属于当前能力。
