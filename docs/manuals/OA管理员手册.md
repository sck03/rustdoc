# OA 系统管理员手册

业务协同平台 · Full

账号与权限 / 组织任职 / 流程规则 / 运行管理

版本日期：2026-11-12　适用程序：0.1.2　数据库基线：schema 17

适用对象：平台管理员、单位管理员、流程管理员、人事与行政管理人员。

正式多人使用采用网页或 Docker + PostgreSQL 18。Full SQLite 便携包可用于培训和验收；Document、Sales 桌面版不提供完整 OA 团队入口。

本手册按现行功能说明操作。示例中的单位、人员和业务均为匿名培训资料。页面只显示当前身份获准的入口；不同权限看到的按钮可能不同。

## 01 阅读路线与开通顺序

先建立真实组织和人员，再配置账号权限，最后发布流程。反过来操作容易出现“没有可用审批人”“当前身份不可用”等问题。

| 顺序 | 操作 | 完成标志 |
| --- | --- | --- |
| 1 | 部署当前程序，创建全新数据库，完成首次管理员初始化 | 能登录 Full，页面时间和单位正确 |
| 2 | 建立单位、部门、岗位及负责人 | 组织层级无循环，负责人来自有效人员 |
| 3 | 建立人员档案和任职，关联登录账号 | 人员、账号、任职一一核对，不靠同名匹配 |
| 4 | 配置权限方案、单位身份和明确限制 | 试用账号只能查看/操作获准数据 |
| 5 | 配置工作日历、办理分工及审批规则 | 每个必经节点都有合格责任人 |
| 6 | 仿真并发布，完成一笔真实测试流程 | 申请、签署、办理和归档形成闭环 |

日常处理顺序：查看流程异常与未完成任务 → 处理人员和授权变化 → 核对计划发布 → 检查备份与任务失败。

不要使用平台维护管理员替代业务人员签署。管理员代填时系统仍区分提交人和实际申请人。

## 02 建立公司、部门与任职

1. 打开“行政与人事 → 组织与任职”，确认当前单位。
2. 在“公司与部门”建立公司和部门。填写稳定代码与清晰名称，核对所属公司和启用状态。
3. 在“任职与岗位”维护岗位目录。岗位名称用于描述职责；写成“经理”不会自动获得审批权限。
4. 建立人员档案后设置部门负责人、公司领导等实际负责人。行政直属上级和职能上级分别填写，不把两种关系混为一项。
5. 在人员任职资料中核对主职、兼职、开始/结束日期、岗位及汇报关系。
6. 用该人员账号重新登录，检查顶部身份选择和申请任职是否正确。

同一个人在同一部门可以担任不同岗位；申请使用明确选定的任职身份，不自动使用第一条。需要跨单位协作时，建立有期限、有范围的单位身份；跨单位身份并不意味着能查看整个集团资料。

正式调岗、离职、返聘等通过“人员变动”办理。不要通过改姓名、工号或直接改数据库伪造任职变化。变动前先处理下属汇报、未签审批和借用品交接。

## 03 建档、创建账号与关联

1. 在人员页面建立公开档案，填写姓名、工号、单位、部门和任职信息。
2. 联系方式、证件等私密资料由获准的人事人员维护；普通通讯录不应出现这些内容。
3. 打开“系统管理 → 账号与权限”，建立登录账号，填写登录名、姓名、状态和初始密码。
4. 按实际需求选择独立授权，或选择明确的已发布权限方案。空独立权限表示无业务权限。
5. 将账号关联到正确人员；核对工号、单位和稳定编号，尤其注意同名人员。
6. 用新账号登录检查人员身份、业务日期、申请入口和可见数据。平台维护账号可不承担业务任职。

已关联账号不能直接替换为另一个账号。需要调整时先确认交接和版本，按界面要求填写原因并解除关联，再选择新账号。解绑保留原档案、账号与历史，不会把旧签署转给新账号。

紧急撤销访问时先停用账号或身份，再处理未结任务。日常离职应先交接后停用。返聘沿用人员身份，但建立新任职期间，不能假定旧账号和旧授权自动恢复。

## 04 设置权限方案与范围

“能看到菜单”“能查看记录”“能执行动作”是三个需要分别核对的结果。

1. 在账号与权限页选择要管理的账号或权限方案。
2. 按模块分类选择业务资源，勾选需要的查看、新建、编辑、审批、办理等动作。
3. 为动作选择适当的数据范围；优先使用满足职责的最小范围。
4. 检查模块开关。关闭模块会收紧最终权限，其他依赖权限不会把它重新打开。
5. 在单位身份授权中明确单位、任职期限、委托上限和显式限制。组织、任职、流程、授权及统计管理可以分别分工。
6. 保存方案草稿，检查差异和影响，发布后选择需要切换的绑定。保存草稿不等于已应用给全部账号。
7. 使用独立测试账号重新登录，实际尝试允许与禁止的操作。

| 要素 | 管理含义 |
| --- | --- |
| 独立授权 | 账号使用明确保存的动作和范围；空集合保持为空 |
| 已发布方案 | 复用受版本管理的配置；修改与应用分开确认 |
| 单位/部门/项目限制 | 对有效权限进一步收紧，必须填写规定的原因 |
| 指定审批/代理/抄送 | 增加明确业务关系，不能越过显式限制 |

修改有效权限后旧会话会失效或要求重新验证；这是撤权生效的一部分。不要用重复登录维护账号来绕过验证。

## 05 按职责配置并验权

以下是分工示例，需按公司制度调整，并非程序自动授予的角色。

| 职责 | 通常需要 | 不应顺带授予 |
| --- | --- | --- |
| 普通员工 | 自助申请、本人进度、所需通讯录和通知 | 全单位审批、全部私密档案 |
| 部门审批人 | 对应 OA 资源查看与审批、合格任职 | 全局账号管理、全部财务办理 |
| 行政办理人 | 指定事项办理、会议/物品交接 | 替业务审批人签署 |
| 财务接收人 | 报销查看与财务接收 | 自动支付权限或总账功能 |
| 人事人员 | 获准的档案、人员变动及交接 | 未授权公司的私密档案 |
| 流程管理员 | 当前单位流程管理、运行异常处理 | 自动取得所有业务材料 |

验权时至少准备申请人、审批人、办理人三个账号。用申请人创建一笔业务，检查本人和他人记录；用审批人检查待我审批、可见材料和禁止自审；用办理人检查批准前不能办理、批准后只能办理分配节点。

再做一次禁止操作验证：停用一个测试身份或收紧部门范围，重新登录后确认旧任务不能继续签署。若有在途分派，按流程交接，不重新放宽权限来掩盖问题。

## 06 流程管理与规则草稿

进入“流程管理”，页面分为流程定义、工作日历、办理分工、审批代理、审批单模板和流程运行。

1. 在“流程定义”选择内置事项并编辑，或点击“新建审批事项”。
2. 在“基本信息”填写便于员工识别的名称。
3. 在“节点图”设置审批决定阶段和批准后的实际办理阶段。
4. 在“抄送与通知”选择需查看进度的账号。抄送不等于审批授权。
5. 自定义事项在“申请表单”定义材料；内置事项继续使用专用表单。
6. 保存当前流程。其他分区或其他流程的未保存草稿仍保留。
7. 到“版本与历史”核对历史，在“仿真与发布”验证并发布。

保存、发布、停用是不同动作。修改草稿不立即改变已发布规则；停用只阻止新的申请，不抹去已有实例。没有发布过的自定义草稿可以删除；已发布或有计划发布的事项应使用停用/取消计划。

多人同时编辑出现版本冲突时，先保留当前修改并核对另一管理员的版本，再重新载入或重做修改。不要连续提交旧版本。

## 07 设计自定义申请表单

1. 填写事项分类，便于员工在发起申请时查找。
2. 在“适用部门”搜索并勾选一个或多个部门；未选择表示全部部门。可逐项移除，或点击“改为全部部门”。
3. 点击“添加字段”，设置字段名称、类型及必填。根据用途选择单行/多行文字、数字、金额、日期、单选、人员、部门或明细表。
4. 金额字段选择币种；单选字段每行一个选项。人员和部门字段使用系统选项，不要求员工手写编号。
5. 在“显示条件”选择前置字段和比较值，使低频字段按条件显示。隐藏后不保留不可见字段作为新的提交内容。
6. 明细表添加列，排列顺序；员工可添加和移除明细行。
7. 按业务需要勾选提交时必须上传附件，保存后进行仿真和真实草稿验证。

容量边界：最多 100 个自定义事项；表单 40 个字段；明细表 10 列、100 行。金额最多两位小数，数字最多六位。不要通过把大量内容塞入单个字段绕过这些边界。

草稿允许暂时不完整，正式提交统一检查必填、附件、引用和规则。已提交材料及引用名称按当时版本冻结。表单发布新版本后，旧未提交草稿可能需要重新发起，不能静默套入新字段。

## 08 审批人、条件与办理节点

选择责任人来源时，先明确制度要求，再选择人员、部门负责人、直属/职能上级、公司领导、岗位、业务职责或项目负责人。动态来源依赖有效组织资料；没有负责人时应补组织或改规则。

| 规则 | 配置与检查重点 |
| --- | --- |
| 顺序审批 | 后一节点依赖前一节点，核对起点和终点 |
| 并行/会签 | 核对全部同意、任一同意或比例通过及否决政策 |
| 条件分支 | 金额条件必须匹配币种；排他分支设置明确默认路径 |
| 自审与独立复核 | 申请人不能签自己的申请；同一自然人换账号/身份不能重复满足独立性 |
| 材料权限 | 只开放当前节点需要的字段、附件及核验项目 |
| 超时和升级 | 选择工作/自然时间，配置提醒、知会上级或受控移交 |
| 子流程 | 固定已发布版本，核对输入、输出及失败/补偿规则 |

批准后的实际办理必须保留专用节点：报销财务接收、采购验收、人员生效、会议室交接与归还、物品预留/发放/归还等。系统动作可以执行归档或已声明的业务动作，但不会代替人员签署同意。

加减签、指定节点退回等能力由发布政策控制。减签不能删除已签意见，也不能使人数/必经职责/独立性失效。

## 09 仿真、发布与定时启用

1. 打开当前定义的“仿真与发布”，点击“模拟当前流程”检查草稿，或“仿真并发布此流程”。
2. 选择真实、有效的人员任职。管理员不能只填一个显示姓名替代身份。
3. 填写类别、日期、金额/币种、项目和自定义材料等影响路径的样例条件。
4. 查看仿真输出：节点顺序、实际责任人、条件命中、被跳过节点及错误。
5. 至少保留一个成功样例，最多 20 个。金额临界值、不同部门、本人担任负责人、无人可用等情况分别验证。
6. 修正失败原因后重新仿真。选择立即发布或填写未来启用时间，再保存发布。
7. 用普通账号进入“发起申请”，核对新事项及一笔真实测试申请。

定时启用在到期后的后台检查中执行，并复核发布身份、活动版本和启停状态。若人员、权限或版本变化，计划可能进入“待处理”，不会强行覆盖。

在“流程运行 → 定时发布与待处理”检查计划；不再需要的计划点击“取消定时启用”。修改已发布草稿后再次发布会生成新版本，在途申请继续使用提交时的冻结版本。

## 10 示例：部门请假审批

示例制度：员工申请 → 部门负责人批准 → 指定人事办理登记。实际制度、工作日历和假期计算以本单位设置为准。

1. 建立员工甲、部门负责人乙、人事丙的人员档案和有效任职。
2. 甲获得请假申请权限；乙获得该范围的请假查看/审批；丙获得所需办理权限。
3. 在组织资料中将乙设为该部门负责人，确认甲的申请任职属于该部门。
4. 编辑请假流程，审批来源选择部门负责人；保留后续办理节点并配置人事分工。
5. 在工作日历中核对工作日、节假日和调休日。输入未完成的日期应先补完整再保存。
6. 用甲的任职仿真一笔请假，确认路径经过乙，并且不会把甲作为实际审批人。
7. 发布后甲创建草稿、填写假期和原因、提交；乙在待我审批签署意见。
8. 丙在待我办理核对已批准事实并登记实际办理，最后查看记录与审批单。

验证失败例：临时取消乙的合格身份后尝试仿真或办理，应出现明确错误或待处理任务。修复真实任职/权限或交接给合格人员，不用平台管理员代签。

## 11 示例：报销审批与财务接收

示例制度：员工申请 → 业务审批 → 财务接收。报销金额门槛如需分级，由单位自行设定并验证币种。

1. 配置申请人、业务审批人和财务接收人各自的动作权限和范围。
2. 编辑报销流程，设置审批节点与金额条件；保留财务接收节点。
3. 配置核验项目和材料权限，例如财务需要核对费用明细及凭证，其他节点只看业务需要的材料。
4. 对金额小于、等于、大于临界值的样例分别仿真，另测不同币种，不能按汇率未确认的数字直接比较。
5. 申请人填写币种和明细，上传报销单/发票/补充资料，保存草稿后提交。
6. 审批人填写核验结果和意见。缺材料可按规则退回修改，不在意见中伪造附件已齐全。
7. 财务在“待财务接收”检查完整内容，登记接收；状态最终显示已交接财务。

财务接收不代表银行付款，不会自动生成或修改独立的付款打印单。实际付款凭证和外部财务软件仍按本单位的独立制度管理。

## 12 示例：自定义“样品寄送”事项

目标：业务员记录客户、运费、收件部门和样品明细，经业务审核后由行政登记寄送。

1. 点击“新建审批事项”，名称填写“样品寄送”，分类填写“外贸业务”。
2. 适用部门选择业务部门和样品部门，确认其他部门是否应当可发起。
3. 建立客户名称（文字、必填）、运费（金额、CNY）、收件部门（部门引用）、样品明细（品名和数量两列）。
4. 设置业务审批人及寄送办理节点；如果需要凭证，要求提交附件。
5. 仿真选择业务员有效任职，填入匿名客户与样品，检查金额和部门引用。
6. 发布后业务员创建草稿。再次编辑时，收件部门应显示正确名称；修改或移除明细后不能错配人员/部门标签。
7. 审批人核对客户与运费并批准；行政填写寄送结果，按制度记录快递或交接说明。
8. 在完成详情查看真实办理记录并下载审批单 PDF。

后续新增字段时先改草稿、仿真再发布。已提交的旧申请继续保留原表单与签署，不用手工改旧记录让它看起来符合新模板。

## 13 代理、交接与运行异常

审批代理适合有期限的直接委托。配置前确认代理人有效任职和当前权限，设置正确时间范围；代理不能扩大数据范围，也不能绕过同一人员独立复核。

人员离职或权限收紧前，在“流程运行”的未完成任务中筛选原责任人，选择合格接任身份并填写原因。交接保存实际接任人，保留原历史签署。

| 现象 | 管理动作 |
| --- | --- |
| 身份/权限不可用 | 修正真实任职或交接任务；重新验证账号 |
| 系统动作失败 | 打开异常队列，核对错误；有权限时填写原因并重试系统动作 |
| 定时启用受阻 | 检查计划版本、发布身份和当前启用状态；修正后重新安排 |
| 未来人员变动受阻 | 核对生效日、人员版本、交接和执行身份；事实变化时取消未生效变动后重申 |
| 版本冲突 | 保留输入，读取最新状态后再决定；不要连续重发旧版本 |
| 网络中断 | 先核对任务、操作回执和记录，避免重复提交现实业务 |

暂停、恢复和终止须由获准身份填写原因。已有库存发放、场地交接等现实动作时，先按流程完成归还或补偿；终止流程不能抹去这些事实。

## 14 审批单、材料与备份恢复

审批单模板使用统一设计器。修改名称、字段、分页、字体或颜色后，先预览样例，再用真实匿名申请生成 PDF，检查长内容和多级签署的续页。

下载 PDF、历史材料或原件 ZIP 时仍执行当前身份的材料权限。不能因为是管理员、收到通知或知道下载地址，就假定可以取得全部私密材料。审批签署记录也不等于电子印章认证。

日常备份应按业务频率制定并验证恢复。完整灾备计划默认关闭；启用后核对时间、时区、保留数量/天数及 WebDAV/S3 副本测试结果。密码与备份包分开保管。

PostgreSQL 页面中的数据库备份实际为数据库 dump；完整迁移包还包含主密钥和用户模板。只复制数据库文件或只保留 dump，不等于完整服务器迁移。

恢复只能使用当前 schema 17 且模型一致的备份。页面完成授权和暂存后，由部署管理员停止 API，使用独立维护账号执行正式恢复入口；失败保持停止并保留待恢复标记及安全副本。不得删除标记冒充恢复完成。

详细停机、Docker 和命令步骤参见《服务器备份迁移与恢复指南》。恢复后抽查人员/权限、在途任务、附件、未来生效变动和实际 PDF，再开放业务。

## 15 上线与日常检查表

正式上线前，在隔离环境完成以下核对并留存结果。

| 检查 | 验收方法 |
| --- | --- |
| 身份与范围 | 各岗位测试允许和禁止动作；跨部门/跨单位记录不会越权 |
| 申请与签署 | 草稿、提交、退回重提、拒绝、取消和独立复核各跑一笔 |
| 实际办理 | 财务接收、采购验收、人员生效、会议及物品交接形成闭环 |
| 多人并发 | 同一记录并发修改、权限撤销、任务交接能明确报冲突 |
| 输出 | PDF 多页、材料裁剪、原件包和附件下载正确 |
| 恢复 | 备份可恢复，密钥/模板不丢失，原程序和业务数据有保留 |
| 稳定性 | 业务规模下测响应、内存、磁盘和长时运行，不能用编译通过替代 |

每天查看异常和失败任务；人员/岗位变化后检查在途责任；发布规则后抽查真实申请。依赖普通版本检查按月，完整治理按周，漏洞审计每日保留；安全修复不能因为减少运行频率而忽略。

清理只针对已确认无用的隔离测试包、测试库、截图和日志。业务数据、用户备份、官方交接目录、私有补丁与可复用资源不按文件名或时间直接删除。
