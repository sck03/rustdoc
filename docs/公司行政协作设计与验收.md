# 公司行政协作：会议室、物品与人员

## 适用范围与启用

会议室预约、物品领用和人员档案共用现有公司、部门、账号与权限方案。PostgreSQL 服务器／容器团队模式按权限开放员工申请、审批及交接；SQLite 单机全功能版（Full）和独立行政版（Administration）均由操作员集中登记人员、预约与领用。单证员版和业务员版关闭单机行政入口、权限目录及 API。产品版与运行模式由后端统一计算，前端使用返回的能力和 `usesOfficeRegister` 展示对应流程。

在“账号与权限 → 权限方案 → 功能模块”中，“公司行政”分类包含三个模块。行政申请及交接按动作分别授权；人员模块独立提供公司通讯录、人事档案与记录、入职登记、维护档案、任职变动、关联账号。“公司员工”方案提供本人行政申请和本公司通讯录，“行政管理员”提供本公司审批、交接及库存维护，“人事管理员”提供本公司人事档案和任职流程。原单证、业务、财务岗位也具有本人行政申请及公司通讯录能力；行政管理员不会自动获得人事资料查看权。

账号必须关联启用的公司。资源目录和业务记录始终限制在当前账号所属公司，即使管理员或某项操作具有“全部”范围也不能越过公司边界；团队模式的本人、部门、公司范围进一步限制申请记录。资源管理作用于本公司的共享资源。自定义方案的缺失动作不会回退为默认授权。团队模式的审批人与申请人必须不同。

## 单机行政功能

单机全功能版与行政版使用本机 SQLite 和现有运行数据根，初次登录沿用 `admin` 空密码及默认公司／部门。可在“系统管理 → 账号与权限”的组织目录中维护公司和部门，再在“公司行政 → 人员档案”登记员工。员工不需要登录账号，单机模式关闭员工账号关联与双人审批动作。Full 同时保留单证与销售能力，默认进入单证概览；Administration 默认进入人员档案。

1. 预约时从在职人员中按姓名或工号搜索选择，保存后直接成为待使用记录并占用时段；现场交接时登记钥匙发放／开始使用和归还／结束使用。
2. 物品领用登记直接校验可用库存并预留，确认实际发放时扣减在库；取消释放预留，借用物品支持分次归还。库存不足须先补充，不能产生负库存。
3. 登记记录同时保留操作员归属、人员 ID、当时姓名和部门。查询按人员分页，未关联账号的人员也必须结清预约、钥匙与借用物品才能调部门或离职。人员档案中的交接事项可进入具体记录或该人员全部记录。
4. 登记、幂等检查、库存、交接历史和人员任职仍使用同一套服务与事务。团队请求不能传入代登记人员 ID，也不会自动跳过审批。

构建入口：`scripts/build-windows-desktop-run.cmd -ProductEdition Administration -NoPause`；全产品便携／安装器入口从 `scripts/product-editions.json` 枚举四版。行政版与业务员版共用 `core` 依赖锁图，不携带浏览器、PDF/OCR、Excel 分析器及单证资源。各平台打包工作流从同一清单读取能力，行政版使用独立 identifier、`latest-administration.json` 和发布通道；正式 updater 使用 `_ADMINISTRATION` 后缀的公钥、私钥和私钥密码配置，缺失时失败，不借用其它产品版的密钥。Windows Authenticode、macOS Developer ID 和 Apple 公证仍不执行。

## 会议室预约与钥匙交接

管理员维护会议室名称、位置、容量、设备、最长预约时长、提前预约天数及是否需要钥匙。名称按 NFC 和统一规范化键在公司内唯一；停用保留历史。

1. 员工查询会议室日程，填写主题、人数和开始／结束时间，提交待审批申请。日程只公开占用时段和状态，其他人的会议主题与身份仍受数据范围保护。
2. 待审批和已批准预约均占用时段；同一会议室不接受交叠区间，前一场结束时可开始下一场。申请时校验容量、未来预约窗口、至少 15 分钟和会议室最长时长。
3. 获授权的管理员批准或驳回。驳回和取消必须说明原因；员工可以取消自己尚未交接的申请。审批不能由申请人自己完成。
4. 批准后，在开始前 30 分钟至预约结束前，由管理员核对申请人并登记钥匙发放。无需钥匙的会议室使用同一流程登记开始使用。
5. 管理员收到钥匙后登记归还，预约完成。上一场未归还时，即使已超过预约结束时间，也不能给下一场办理交接。使用中的预约不能直接取消。

过期申请不会自动批准或伪造钥匙归还，页面显示过期或超时未归还状态，管理员可处理未交接的申请。存在未来预约或使用中记录时不能停用会议室或更改钥匙规则；降低容量也不能破坏未结束预约的参会人数约束。

## 物品申请、发放、归还与补充

物品区分消耗品和需归还的借用物品。数量使用整数计量单位，如支、盒、台；在库、预留与单次申请均有明确上限。物品已有申请后，单位和归还类型不能改写历史语义。

| 操作 | 申请状态 | 库存效果 |
| --- | --- | --- |
| 提交申请 | 待审批 | 不占库存，缺货时也可提交 |
| 批准 | 待领用 | 原子检查可用量并预留申请数量 |
| 驳回 | 已驳回 | 不扣库存 |
| 取消未交接申请 | 已取消 | 释放已批准的预留数量 |
| 管理员确认发放 | 已领用／借用中 | 同时扣减在库和预留量 |
| 借用物品部分归还 | 仍为借用中 | 按本次实收数量增加在库并记录流水 |
| 借用物品全部归还 | 已归还 | 关闭借用记录 |
| 补充入库 | 独立库存流水 | 增加入库数量，记录说明及操作人 |
| 库存盘点 | 独立调整流水 | 记录盘点差额；不能低于已审批预留量 |

可用量等于在库量减预留量，低于或等于最低可用库存时显示提醒。借用物品必须填写预计归还日期；审批和发放都会复核期限，逾期未归还记录保留在管理员工作区。库存补充和盘点使用独立操作标识，重复提交同一操作不会重复入库。

处理记录包含操作、实际数量、操作人、时间和说明；库存流水保留每次增减及变动后库存。纠正库存使用新的盘点流水，不改写已有记录。

物品卡片默认展示申请／登记和补充库存；库存流水、盘点及编辑位于“更多操作”，展开后按当前权限显示。领用与归还记录仍在页内独立标签处理。

## 一致性与实现边界

- 八类实体进入当前业务库：`MeetingRooms`、`MeetingBookings`、`OfficeSupplies`、`OfficeSupplyRequests`、`OfficeRequestEvents`、`OfficeStockMovements`、`PersonnelEmployees`、`PersonnelEvents`。资源、申请、部门归属与历史使用公司组合外键，库存与状态有数据库约束；人员关联账号全库唯一且禁止删除有人员或行政历史引用的账号。
- 团队写操作先取得相应会议室／物品的 PostgreSQL 行锁，再检查冲突、预留或扣减；单机使用 SQLite 写事务。业务状态、交接记录和库存流水在同一事务提交；资源保存和申请处理同时使用 `ExpectedVersion`，防止过期界面覆盖他人的操作。
- 创建申请使用账号与公司内的请求标识，相同标识和相同内容返回原申请，不同内容拒绝复用。重复审批、发放或归还不能产生第二次状态变化或库存增减。
- 请求有 30 秒上限，调用方取消会传播；事务回滚另有 5 秒上限，保留原始错误。数据库故障继续映射依赖不可用，不伪装为预约冲突或空列表。
- 时间点使用 `DateTimeOffset`，存为 UTC；页面按公司业务时区输入和显示，查询自然日考虑夏令时。借用归还日使用 `DateOnly`。
- 列表、处理记录和库存流水均分页；日程单次最多查询一周。查询／变更／轮询集中在 hook，表单解析、状态展示和权限判断集中在纯模型；页面只组合展示。后台标签页不持续轮询，写请求不自动重试。
- API 由官方 OpenAPI 元数据生成，Web 使用生成客户端。没有新增 NuGet、npm、Rust 依赖、第二数据库、默认文件目录或浏览器持久化。
- 空库基线为 **v16**，与单据核对、业务资料和个人待办共用。按项目未投产规则，旧开发库不执行猜测迁移或双读；需要保留的开发数据先备份，再用空库初始化。团队模式仍采用一个 API 实例、多浏览器用户的部署方式。本次 Full 开放行政能力不改变数据库结构。

## 人员信息与入转离闭环

人员档案与登录账号分开：不需要使用系统的员工也能建立档案。工号在公司内按 NFC 和规范化键唯一，档案包含姓名、部门、岗位、用工类型、入职日期、试用与合同截止日期、工作联系方式、个人电话、紧急联系人和人事备注。列表按部门、状态和关键词分页查询；人事人员可以筛选已到期或 30 天内到期的试用／合同事项。

公司通讯录只返回工作信息；个人电话、紧急联系人、任职日期及人事备注由独立 `view-details` 动作保护。档案、历史、交接清单及写入都校验对应动作的数据范围。公司、部门和本人范围不会被“有查看权”替代，跨公司始终拒绝。只有本人范围的创建权限不能创建无关联账号的档案，界面也不会开放入职入口。

1. **入职登记。** 选择启用部门，登记实际入职日期和试用／正式状态。重复提交同一登记标识不会重复建立档案；公司行锁与唯一键覆盖 PostgreSQL 并发登记。
2. **关联账号。** 系统管理员从同公司同部门的启用普通账号中搜索选择，提交时核对人员与账号两个版本号。姓名和部门此后由人员档案维护；关联关系保留用于追溯，不能随意换绑。管理员账号单独维护，账号创建、密码和权限方案继续使用现有账号界面。
3. **转正与调岗。** 转正只接受试用状态；部门／岗位调动保留变更前后信息。调动前后均校验数据范围，更换部门须结清行政事项。关联账号同步部门并撤销会话；既有业务单据保留原归属，不把历史记录批量转移到新部门。
4. **离职交接。** 人事先查看交接清单；待审批、待交接申请、使用中会议室及尚欠借用物品都会阻止离职。行政人员可从清单跳转到具体申请，取消未交接申请、归还钥匙或借用物品。每类清单显示前 20 笔，另可按人员分页查看全部申请。
5. **离职归档。** 服务端再次检查交接，事务内保存离职状态、停用关联账号并撤销数据库会话，API 随后清除会话验证缓存。账号页不能绕过离职流程重新启用账号。新增行政申请与离职共同锁定账号行，避免“清单已清空”与新申请并发穿透。
6. **返聘。** 保留原工号和完整历史，开始新的任职周期。原账号维持停用，由系统管理员复核权限后启用；合同与试用期限重新登记。离职归档没有硬删除入口。

任职命令必须填写说明，生效日期不得早于上一次任职变更或晚于公司业务日期。操作立即生效，不将填写未来日期误作已实现的定时流程。写入、历史及会话撤销在同一业务库事务协调，不引入 HR 服务、消息队列、第二数据库、文件上传目录或浏览器持久化。人事操作记录记录变更字段和任职事实；通用审计继续使用既有脱敏规则。

当前功能面向内部通讯录和基础人事管理，不包含薪资、考勤、招聘或外部身份供应商同步。

## 方案参考与验证入口

参考 [Microsoft Exchange 资源邮箱](https://learn.microsoft.com/en-us/exchange/recipients-in-exchange-online/manage-resource-mailboxes) 的预约窗口、时长限制、冲突检查和代理审批，结合公司线下钥匙管理形成交接闭环。参考 [Odoo 库存补充规则](https://www.odoo.com/documentation/19.0/applications/inventory_and_mrp/inventory/warehouses_storage/replenishment/reordering_rules.html) 的可用库存及补充提示，采用适合当前项目的人工补充、审批预留和不可覆盖流水。

人员模型参考 [Odoo 员工档案](https://www.odoo.com/documentation/19.0/applications/hr/employees/new_employee.html) 的工作信息、部门岗位和个人资料分区，以及 [Microsoft Entra 生命周期工作流](https://learn.microsoft.com/en-us/entra/id-governance/what-are-lifecycle-workflows) 的入职、调岗、离职、权限撤销和可追溯历史。仅借鉴业务流程，不依赖这些产品或其商业许可。

- `OfficeServicesTests`：状态流转、归属隔离、预约冲突、超时钥匙、库存预留、部分归还、重复提交、过期借用、取消与分页。
- `ApiOfficeAccessTests`：四产品版模式限制、单机 Document／Sales 的 API 拒绝、真实 HTTP 认证／授权／申请／审批／交接和功能模块目录。
- `OfficeLocalRegisterTests` / `ApiAdministrationEditionTests`：Full／Administration 全新 SQLite 登录、组织目录、无账号人员登记、库存预留／取消／分批归还、按人员查询、离职阻塞和团队代申请拒绝。
- `OfficePostgreSqlScenarios`：由 PostgreSQL 集成验证调用，检查并发预约、竞争审批、重复交接／入库、取消与发放竞争以及流水和库存一致性。
- `PersonnelServiceTests` / `ApiPersonnelAccessTests`：人员状态、工号、私密字段、动作范围、账号绑定、离职交接、会话撤销、组织停用和官方 OpenAPI。
- `PersonnelPostgreSqlScenarios`：真实 PostgreSQL 下并发幂等入职、过期调岗版本及离职／申请竞争。
- `npm --prefix apps/export-doc-web run test:office-models`：权限与深链、公司业务日期、夏令时、状态显示及可信内网 HTTP 的请求标识。
- `npm --prefix apps/export-doc-web run test:office-ui`：真实 React 页面、账号与权限中的模块修改保存、桌面／手机、表单交互、嵌套确认与无障碍。

准确的本轮通过数量、环境和外部验收边界见《当前架构事实》与进度文档的最新日期记录。
