# 备份、整机迁移与恢复指南

> 2026-10-14。Docker／非容器网页版使用 PostgreSQL 18，桌面版使用 SQLite。入口统一为 **系统设置 → 备份与恢复**。部署步骤见 [Docker](./Docker容器部署与启动指南.md)和[网页版](./网页版部署与启动指南.md)。

## 1. 选择合适的恢复材料

| 材料 | 内容 | 用途 |
| --- | --- | --- |
| `.edmmigration` | PostgreSQL 快照、凭据主密钥、用户文件模板，整体加密 | 服务器整机迁移、完整灾备与恢复 |
| `.edmrecovery` | SQLite 快照、凭据主密钥、用户文件模板，整体加密 | 桌面换机及完整恢复 |
| `.dump` | PostgreSQL custom-format 数据库快照，本身不加密 | 保留原 DataRoot／密钥时的数据回退 |
| `.sqlite3` | 桌面数据库快照 | 当前安装内的数据回退 |
| 部署配置副本 | Compose／RuntimeConfig、网络代理、TLS 证书、服务托管配置及运维记录 | 恢复部署环境，需另外保存 |

业务单据、账号、设置、图片、OA／人事／业务附件、数据库模板和历史均在业务数据库中，随快照一起备份。文件任务中仍存储于数据库的内容随库恢复；磁盘上的任务输出、既有备份、交接目录、日志和缓存不属于完整包承诺，必要输出请另存。

完整包中的主密钥用于解密原凭据和授权身份。只有数据库快照而缺少匹配的主密钥，不能保证恢复后可用。完整包不重置授权期；桌面更换机器仍需要按机器绑定重新激活。

旧 API 中 `PhysicalBackup` 的名称保留契约兼容性，实际执行的是 `pg_dump` **逻辑快照**，不是复制原始 PostgreSQL 数据目录或 WAL 时间点恢复。

## 2. 日常灾备：默认关闭

“日常灾备”页面默认不启用定时执行。先设置并单独保管备份包密码，点击“保存灾备设置”，即可使用“立即备份一次”；这不要求开启日常计划。

需要自动执行时：

1. 勾选“启用日常灾备”，选择每天或每周以及执行时间。
2. 核对页面显示的业务时区，建议安排在业务低峰。
3. 展开“保留策略”，设置最新份数以及可选的保留天数。天数为 0 时只按份数保留。
4. 在“异机副本”中选择远程存储并测试；也可暂时只保存在本机。
5. 保存设置，检查下次执行时间，并手动执行一次，确认本地包和副本结果。

服务必须保持运行。调度以业务自然日去重；启动时补做当天已到时间但未执行的计划，不补生成过去停机数日的重复全量包。备份资源繁忙时延后重试。原来的历史自动备份字段不会自动开启新计划。关闭计划停止定时线程，已经启动的文件任务可单独取消。

完整包保存在 **`DataRoot/Backups/ScheduledRecovery`**。页面显示最近 20 份，支持下载和直接用于恢复。密码只加密存储，不回传；新密码至少 12 个字符，建议使用密码管理器生成。更换密码只影响后续新包，旧包继续使用创建时的密码。

## 3. 异机副本：WebDAV 或 S3

先保存配置，再点击“测试已保存的副本存储”。测试会创建本次独有的小文件，实际验证写入、回读校验和删除；测试文件随后清理。保存配置本身不会上传业务数据。

### WebDAV／NAS

填写已存在的备份目录 URL、用户名和密码。支持管理员明确配置的局域网 IP／主机名和 HTTPS；证书由系统信任链校验。账户需要目录创建、写入、读取、移动和删除权限。

程序在该目录下创建 `exportdoc-recovery-<仓库编号>`，先上传临时文件，按选项回读校验，再通过 WebDAV MOVE 发布正式副本。上传失败或取消时清理本次临时对象。历史 SQLite WebDAV 快照的手工入口保留在桌面的“恢复与校验 → 历史 WebDAV 数据库副本”，默认折叠且不自动访问远端。

### S3／兼容对象存储

填写 API 端点、区域、桶名、对象前缀、Access Key ID 和 Secret Access Key。大多数 NAS／MinIO 使用路径寻址；AWS 也可采用虚拟主机寻址。使用临时凭证时另填 Session Token，并在过期前更新。桶须预先存在。

程序使用官方 AWS SigV4 签名库和显式凭据，不读取机器上其它 AWS 凭据，也不调用实例元数据服务。密钥加密保存，界面只显示是否已配置。

对象位于 `<前缀>/<仓库编号>/<文件名>`。账户需要该前缀的对象读取、写入、删除及中止分段上传权限；普通上传不需要创建桶或列举其它桶。采用服务端分段上传，按对象大小调整分段，逐段读取文件，不把整段大文件留在内存；临时失败可重试同一段。失败或取消会中止未完成上传，清理失败在任务中记录。建议桶另外配置未完成分段生命周期，以处理服务器突然断电等无法执行清理的情况。

S3 的分段数量、单段和单对象边界仍由存储服务决定。开启桶版本控制后，删除当前对象不等于删除所有历史版本；历史版本和保留锁由存储端生命周期策略管理。

### 成功与失败的含义

默认启用“上传后完整回读并校验 SHA-256”，它会增加一次完整下载流量；校验通过显示“已回读校验”。关闭时只显示“已上传”，不能当作完成了回读验证。

本地完整包写入成功后才上传副本。副本失败显示“部分完成”，保留本地包和旧备份，本次不执行保留清理。新备份及所选副本均成功后才按保留策略删除到期／超额项，至少保留最新一份。清理只处理本仓库登记且摘要匹配的文件，不按文件名或修改时间扫描删除管理员资料。

切换存储地址或账户后，不使用新配置删除旧目标上的对象。旧目标副本由管理员自行保留或清理。恢复到另一安装、仓库编号不匹配时，自动计划会关闭并提示复核，避免新机器继承旧机器的清理职责。

## 4. 大容量包如何处理

**新格式不设置 256 MiB、1 GiB 或 64 GiB 的固定总容量额度。** 文件压缩使用 ZIP64；密封格式 v2 使用 1 MiB 的 AES-256-GCM 认证块，认证块序号、长度和结束标记，拒绝篡改、缺块、截断及尾部追加。复制和摘要使用固定缓冲区；HTTP 上传暂存到受管磁盘，下载从文件流式发送。

v1 合法包仍可读取，保留其旧格式容量边界。包内路径、清单、文件数、数据库版本及主密钥校验继续有效；附件主要在数据库快照中，不占用额外 ZIP 文件条目。总容量不设额度不代表没有磁盘、协议和时间限制。

- 创建时可能同时存在数据库快照、压缩中间文件和加密输出，恢复时还需要解压暂存及恢复前安全副本。按实际数据规模预留空间，不只按压缩包大小估算。
- 解压前检查展开大小与剩余磁盘空间；空间变化或 I/O 故障会使任务失败并保留可检查状态。
- 备份任务和大包上传有 24 小时的总时限；存储网络的单次阻塞读写有 30 秒边界，失败可查任务结果。
- 代理须允许相应请求大小和时长，并关闭大文件请求缓冲；公司网关或公网 CDN 的限制仍可能更小。
- 超大包优先在服务器／备份存储之间搬运，再从服务器目录导入。现有完整包可以通过网页按编号直接恢复，避免浏览器往返。

内部认证分块及 S3 分段不等于可断点续传的浏览器上传，也不等于外部分卷归档。当前发布物仍是一个完整文件；若外部介质要求分卷，管理员应在搬运后原样拼回并验证摘要，再交给程序恢复，不能修改包内清单或版本标记。

## 5. 整机迁移

1. 在目标服务器部署相同或支持该数据库版本的较新程序，使用新的空 PostgreSQL 18 业务库和独立凭据。
2. 只让管理员访问目标；使用目标初始化口令创建临时管理员。
3. 切换前暂停源站录入，完成必要文件任务，在“整机迁移”创建最后一份完整包。另存部署配置及需要保留的外部输出。
4. 停止源应用，保留源数据和备份。
5. 在目标“恢复与校验 → 从外部完整包恢复”选择包，输入目标管理员密码、原包密码及 `MIGRATE`。
6. 校验暂存成功后，对目标执行下一节的离线维护；恢复后用**备份中的账号密码**登录。
7. 检查数据、权限、附件、模板、PDF 和授权，再切换 IP／域名。不要让两边同时接收业务录入。

目标继续使用目标自己的数据库登录角色和连接文件，不需要覆盖为源服务器的数据库密码。完整包可以在 Docker 和非容器 PostgreSQL 部署之间迁移。SQLite 桌面库不直接还原到 PostgreSQL；旧 C# 库及早期试验 schema 不属于兼容迁移范围。

## 6. 恢复与维护窗口

恢复会把整个业务库回到备份时的状态，备份之后的新记录和权限变更会回退。安排前先为当前状态另存完整包，暂停业务录入。

“恢复与校验”提供三种来源：本地已登记完整包、外部完整包、数据库快照。完整包需要创建时的密码；恢复既有包不套用新密码强度要求。PostgreSQL 需管理员重新认证，并输入 `MIGRATE` 或 `RESTORE DATABASE`；桌面完整恢复使用 `RECOVER`。

从本地完整包恢复是后台校验任务。任务成功或网页显示“恢复已暂存”仅表示准备完毕，数据尚未替换。PostgreSQL 必须停止 API，由独立维护进程执行；普通重启不自动恢复。

### 镜像 Compose 部署

在原 Compose 目录逐条执行，确认每条成功后再执行下一条：

```sh
docker compose stop application
docker compose run --rm --no-deps restore
docker compose up -d --no-deps --wait application
```

### 非容器网页部署

停止 API，使用原 AppRoot、DataRoot 和 RuntimeConfig：

```sh
/srv/exportdoc/app/ExportDocManager.Server --app-root /srv/exportdoc/app --data-root /srv/exportdoc/data --restore-pending
```

Windows 使用对应 `.exe` 和实际目录。采用旧的显式连接文件配置时，继续传入原业务及维护连接环境变量；两者必须指向同一数据库。只有维护成功后才启动业务服务。

### 直接导入服务器上的大包

停止 API，准备管理员私有的包密码文件，然后执行：

```sh
/srv/exportdoc/app/ExportDocManager.Server --app-root /srv/exportdoc/app --data-root /srv/exportdoc/data --import-migration /srv/exportdoc/import/company.edmmigration --package-password-file /srv/exportdoc/private/restore-password.txt
```

该命令取得维护锁后完成暂存和恢复。Docker 可把包放在主机 `data/Backups/Imports`，密码文件放在 `config/maintenance`，确保容器内 UID 10001 可读取，再执行：

```sh
docker compose stop application
docker compose run --rm --no-deps restore --app-root /opt/exportdoc --data-root /var/lib/exportdoc --import-migration /var/lib/exportdoc/Backups/Imports/company.edmmigration --package-password-file /run/exportdoc-maintenance/restore-password.txt
docker compose up -d --no-deps --wait application
```

第二条失败时不要执行第三条。恢复完成后按公司制度保管包，删除本次临时密码文件；密码不出现在命令行参数中。

桌面版完整恢复校验成功后退出并重新打开程序，在数据库打开前持实例锁完成恢复。普通 SQLite 数据库快照恢复完成后需重新登录。

## 7. 故障保护与恢复验收

恢复前保存原数据库和文件副本，校验 schema、文件摘要、路径及实例锁。PostgreSQL 维护与业务账号分离；维护失败不启动业务 API。失败保留 `.pending-restore.json`、安全备份、恢复日志及暂存目录，不删除标记强行启动。

PostgreSQL 普通恢复安全副本位于 `Backups/PostgreSQL/safety-<编号>`；完整迁移的恢复现场位于 `Backups/ServerMigration/pending-<编号>`。恢复程序会尝试事务及文件回滚；回滚失败明确停止，须管理员依据安全副本检查。

验收至少包括：备份中的管理员及普通员工登录；抽查新旧单据、OA 和历史；下载附件并核对；查看图片、私人及共享模板；生成 PDF 并核对金额；查看授权和凭据状态；检查新计划是否需要重新配置。记录包摘要、版本、开始／结束时间及检查结果，在隔离目标定期演练。

当前数据库采用全新 schema 9，仅支持 schema 9 的数据库及备份。此次生产部署前重构删除旧试验库迁移链，旧包不会被自动升级或覆盖。需要重建时，先关闭旧程序并保留需要的原数据/备份，再显式使用新 DataRoot 或新 PostgreSQL 数据库初始化；不能修改 schema 标记伪装兼容。PostgreSQL 主版本升级、程序回退与业务库恢复分别验证。

## 8. 更大规模公司的长期灾备

当前程序内建的是**可跨部署恢复的定期完整加密快照和异机副本**。前端只提供实际执行的功能，没有把增量备份或 WAL/PITR 显示成可用开关。

如果公司要求分钟级恢复点或数据库达到频繁全量备份成本很高的规模，应在 PostgreSQL 运维层部署 pgBackRest／基础备份加 WAL，并配置独立备份账户、归档存储、保留周期和恢复演练。WAL 归档需要数据库服务器配置和运维权限，普通业务 API 不获得这些权限。主密钥、用户文件模板及部署配置需与对应恢复点配套保存。

两条恢复路线各有用途：程序完整包便于迁机和跨部署恢复，原生 PostgreSQL 灾备适合增量及时间点恢复。仅复制运行中的 PostgreSQL 数据目录、只保存 Docker 镜像或 PDF，都不能替代它们。对于很大的附件库，当前附件仍与数据库保持同一事务和快照；将来若改为对象存储，须同步升级包清单、附件存储边界和恢复一致性协议，不能只修改一个上传目录。
